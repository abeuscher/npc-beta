## Production deployment notes

An **existing** deployed database has the two portal tables but not the two new migration rows, so a plain `migrate` would try to re-create existing tables and fail. One-time step per environment (the 390/393 precedent; the local dev database was walked this way in-session):

- **Disposable data** (demo droplet, auto-deploy server): `docker exec nonprofitcrm_app php artisan migrate:fresh --seed --force`.
- **Data must be kept:** mark the two plugin migrations as applied, then `migrate` behaves normally:

  ```
  docker exec nonprofitcrm_postgres psql -U postgres -d <db> -c \
  "INSERT INTO migrations (migration, batch) SELECT unnest(ARRAY[
     '2026_08_20_000001_create_portal_accounts_table',
     '2026_08_20_000002_create_portal_password_reset_tokens_table']),
     (SELECT coalesce(max(batch),0)+1 FROM migrations);"
  ```

Fresh installs need nothing special. The deploy image build now fetches `nonprofitcrm/member-portal` v0.1.1 from GitHub (public, credential-free) — no pipeline change. Deploy already runs `widgets:sync` + `build:public`, which picks up the vendor-relative portal script paths (verified locally; handles unchanged). VERSION bumped 0.394.01 → **0.395.01**.
