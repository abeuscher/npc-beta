## Front-loaded decisions (settled at 376 prompt-draft time — do not reopen in session)

1. **Location & namespace.** In-repo plugins live at a top-level `plugins/` directory: `plugins/{PascalName}/`. PSR-4 namespace `Plugins\{PascalName}\`, added to `composer.json` autoload as `"Plugins\\": "plugins/"`.
2. **Pilot selection.** Prefer a clean leaf widget carrying **both** JS and SCSS so the asset seam is exercised end to end. Check LogoGarden first (`app/Widgets/LogoGarden/`); if it lacks one asset type, pick the cleanest data-contract-path widget that has both (consult `widget_types.assets`). BarChart (JS, no SCSS) is the fallback if nothing clean has both — note the gap in the log. "Clean" = renders only `$config` + `$widgetData` via the data-contract path; no model calls in the template.
3. **Registration mechanism.** A new `config/plugins.php` returning an ordered list of plugin service-provider class strings; core registers each during bootstrap (implementation detail — `bootstrap/providers.php` vs. a small core loader reading the config — is the session's call; prefer whatever keeps "remove the line = plugin gone" true, since this list is the in-repo miniature of the future manifest/activation layer). The pilot's provider registers its `WidgetDefinition` into the existing `WidgetRegistry` (`app/Services/WidgetRegistry.php`) — the registry API itself does not change.
4. **Views.** The pilot's provider registers its own Blade view namespace (e.g. `plugin-logo-garden::`); the definition overrides `template()` accordingly. The shared `widgets::` namespace (pointing at `app/Widgets`) stays untouched for the other 40.
5. **Assets.** The definition's `assets()` paths move to `plugins/{Name}/…`. `AssetBuildService::collectSources()` reads repo-relative paths from `widget_types.assets` off disk, so this should Just Work after `widgets:sync` — verify, don't assume: run `widgets:sync` then `build:public` and confirm the manifest carries the pilot's bundles.
6. **Core cleanup.** The pilot's definition class, `use` import, and `register()` line are **removed** from `app/Providers/WidgetServiceProvider.php`. The old `app/Widgets/{Name}/` folder is gone at session end (moved, not copied).
7. **Contract doc.** `docs/plugin-contract.md` v0.1.0, versioned FM-style (version header + changelog). Structure: the 13 surfaces from the plan doc §4c, each marked **PROVEN** (exercised by the pilot: registration, widget contribution, views, front-end assets) or **DECLARED** (specified, not yet exercised). Plus the settled rules as normative text: relations-on-`contact_id` only; verticals never depend on verticals; hard deps point only at core, soft deps at foundation plugins via capability detection; disabled = inert (no routes, no nav, no scheduler jobs, writes stopped, data kept); the three Filament conventions; plugins never patch plugins.

## Phases

### Phase 1 — Extraction

Move the pilot to `plugins/{Name}/`, stand up its service provider, wire `config/plugins.php`, remove it from core registration. Behavior-preserving throughout: same handle, same `widget_types` row content after `widgets:sync` (the jsonb key-order caveat from the 375 log applies to any comparison).

### Phase 2 — Prove the seams

`widgets:sync` idempotent with the pilot registered from the plugin; `build:public` green with the pilot's assets in the manifest; the pilot renders on a public page identically to before (Pest evidence, adapting existing widget render tests; add a registration test: provider registered → registry contains the handle, config line removed → registry lacks it).

### Phase 3 — Contract doc v0.1

Write `docs/plugin-contract.md` per front-loaded decision 7, from what Phases 1–2 actually proved.

- `docs/plugin-contract.md` v0.1.0 exists with every surface marked PROVEN or DECLARED.
