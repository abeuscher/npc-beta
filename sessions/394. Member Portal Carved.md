## Front-loaded decisions

1. **Shape:** `plugins/MemberPortal/`, namespace `Plugins\MemberPortal\`, provider `MemberPortalServiceProvider`, derived handle `member-portal`, package name (later) `nonprofitcrm/member-portal`. `distribution.json` gains a `folder` entry, appended last (sixth provider line); registration order after the verticals is fine — capability declarations happen at `register()`, which completes for all plugins before any `boot()` runs.
2. **The auth stack moves with the plugin.** Guard + provider + password-broker entries injected into `config/auth.php` from the provider's `register()` (the Payments config-injection precedent); the `portal.auth` alias registered in `boot()` via `Route::aliasMiddleware` (`PortalAuthenticate` moves into the plugin). First plugin-owned guard/alias — record on surfaces 1/4 at the contract bump. `config/auth.php` keeps no portal entries; the `auth('portal')` reads that stay core (`portal_member` arm, `FormSubmissionController`) must behave on a portal-absent composition — `auth('portal')` with no such guard **throws**, so the core reads gate on capability presence (decision 3's signal; the arm returns `['item' => null]`, the collision check skips — package-phase identity checks arbitrate what else trips, but these two are known and gated at the carve since the removal mirror exercises them immediately).
3. **The `member-portal` capability (surface 13's second shipping capability) is the presence signal.** Declared at `register()` (`provide('member-portal', fn () => true)` — presence-is-enablement; no credential dimension like Payments'). Consumers: the Events portal route (decision 4), the two core `auth('portal')` reads (decision 2), and any future portal-presence check (the package phase's composition-safety work inherits the signal).
4. **The Events rider release — `crm-plugin--events` v0.1.2** (the 389 rider mechanics: contract wording first, sibling checkout edit, tag, core lock bump + `^0.1` constraint unchanged in composer.json + distribution.json, same-commit): `portal.events.register` registers only when `CapabilityRegistry::present('member-portal')` — with the portal absent the route vanishes (404/405 per the catch-all, the established vanish shape) instead of 500ing at dispatch. Events-without-Portal joins the presence matrix (the Events-without-Payments precedent, surface 13).
5. **`portal_password_reset` stays a core-owned template handle this session.** Surface 7 marks it core "permanently" — that wording predates the portal carve; moving it to the plugin's registry contribution is a one-handle follow-up recorded at close (contract note), not carve freight. The traveling `PortalPasswordReset` mailable keeps consuming it via `EmailTemplate::forHandle()` (core API — legal from plugin code).
6. **Models, factories, schema, seeders stay core this session** (§ 6.7; the package phase moves the two tables and gates the seeders). The carve moves behavior only.
7. **Testsuite:** new `MemberPortal` phpunit testsuite at `plugins/MemberPortal/tests/` (rule-5 pass with logged reduction); twin fixtures `MemberPortalRemovedTestCase` + `MemberPortalDisabledViaFlagTestCase` (no migrator path — the expiring caveat, 392 wording); boundary guard `MemberPortalModuleBoundaryTest` (zero `Plugins\MemberPortal\` references in `app/`, zero allowlist, positive control). New coverage: the capability declaration, the Events-without-Portal matrix cell (rides the vendor'd Events suite or a core-side presence test — decide per where the assertion naturally lives), the two gated core reads on the removal mirror.
8. **Block shape after the carve (decide at this session's close, not now):** the package phase is a two-table redraw with a sequence (`portal_accounts_id_seq` — the donations mechanics) plus the portal-absent composition-safety hunt (page topology, seeders, the type-`member` page gate — likely richer than D4's). One combined closing session (the D4 precedent) or two, per what the carve surfaces.
9. **Contract doc at close: 0.17.0 → 0.18.0** — surface 13 second capability + its Events consumer; surfaces 1/4 plugin-owned guard/alias notes; the surface-7 follow-up note (decision 5); changelog.
