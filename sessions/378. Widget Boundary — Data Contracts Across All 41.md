## The survey (ground truth, captured at 377 close)

Twelve of 41 templates reach outside the contract path. Re-verify at session start; the categories drive the phases.

**A — direct model queries (3):**
- `DonationForm` — `\App\Models\Fund::where(is_active, !is_archived)->orderBy(name)->get()`
- `Nav` — `\App\Models\NavigationMenu::find($menuId)` + an `app(GradientComposer::class)` call
- `PortalSignup` — `\App\Models\MembershipTier::where(is_active, !is_archived)->orderBy(sort_order)->get()`

**B — SiteSetting brand reads (3):** `PortalLogin`, `PortalForgotPassword`, `PortalSignup` — `\App\Models\SiteSetting::get('site_name', config('app.name'))`.

**C — portal auth state (5):** `PortalAccountDashboard`, `PortalChangePassword`, `PortalContactEdit`, `PortalEventRegistrations` — `auth('portal')->user()` drives logged-in/out rendering; `EventRegistration` — reads `auth('portal')` for member prefill **in addition to** its existing event contract (the two-source case).

**D — super-admin tool widgets (2):** `SetupChecklist`, `RandomDataGenerator` — `auth()->user()?->isSuperAdmin()` gate + `app(...)` service calls for their data.

The remaining 29 templates read only `$config` / `$configMedia` / `$widgetData` / `$pageContext` — already clean; widgets that consume no data keep `dataContract(): null`.

## Front-loaded decisions (settled at 377 prompt-draft time — do not reopen in session)

1. **Multi-contract widgets.** `WidgetDefinition` grows `dataContracts(array $config): array` — an array of **named** contracts (`['event' => …, 'member' => …]`). Default implementation wraps the existing singular `dataContract()` so the 20 existing single-contract widgets are untouched, and single-contract widgets keep today's unkeyed `$widgetData` shape (`['items' => …]` / `['item' => …]`) — no template churn outside the twelve. Multi-contract widgets receive `$widgetData` keyed by contract name (`$widgetData['member']['item']`). `WidgetRenderer` resolves the list through the existing `ContractResolver::resolve()` (which already accepts a list); `mergeUserQueryConfig` applies only to the widget's primary (first) contract.
2. **New resolver arms** (all fail-closed per-field, following the existing arm pattern):
   - `fund` (list) — for DonationForm; active/non-archived scope lives in the arm, not the template.
   - `navigation_menu` (CARDINALITY_ONE, id filter) — for Nav; the menu's tree projects through declared fields.
   - `membership_tier` (list) — for PortalSignup.
   - `portal_member` (CARDINALITY_ONE) — resolves `auth('portal')->user()` inside the arm and projects **only contract-declared fields** (member + linked contact prefill fields). Logged-out = `['item' => null]`, which is exactly the branch the templates already take. This is the PII-sensitive arm: ship a non-leak test (undeclared fields never appear in the DTO) alongside the happy path.
   - `setup_checklist` and `scrub_counts` (service-backed, CARDINALITY_ONE) — the arm itself hard-gates on super-admin and returns the empty shape otherwise; the template's auth check dissolves into "no data → render nothing", which is its current behavior.
3. **Site name via page-context tokens.** Add `site_name` to `PageContextTokens::TOKENS` (a grep-visible, reviewed addition per the documented pattern — it is public brand metadata). The three category-B templates declare `SOURCE_PAGE_CONTEXT` contracts (or extend their new ones) and read it from `$widgetData`; the `config('app.name')` fallback moves into the token's value computation.
4. **Nav's GradientComposer call** moves out of the template — either precomputed into the nav contract's DTO or extracted behind a shared Blade component under `resources/views/` (core view infrastructure, outside the guard's scan). Session's call; log it.
5. **The standing guard test** (new, the pinned-list `DesignGroupIntegrityTest` pattern): scans `app/Widgets/*/template.blade.php`, `plugins/*/template.blade.php`, and `resources/views/widget-shared/*` sources and fails on `\App\Models`, `DB::`, `Auth::`, `auth(`, `app(`, `@inject`, `::where(`, `::find(`, `resolve(`. **Zero allowlist at session end** — the twelve are fixed, not exempted. Core Blade components (`<x-picture>` etc.) remain out of scope of the scan.
6. **Rider (absorbed from the 377 capture buffer):** `WidgetManifestTest`'s screenshot-path check still assumes `app/Widgets/{Folder}`; resolve it from the definition's own directory (the `thumbnailDir()` precedent — add a sibling `screenshotDir()` or generalize; session's call).
7. **Contract doc:** at close, update `docs/plugin-contract.md` surface 2 to record the template-purity rule as enforced (guard named), the multi-contract shape, and the new arms; version bump + changelog per the doc's discipline.

## Phases

### Phase 1 — The seam: multi-contract plumbing

`dataContracts()` on the definition base, `WidgetRenderer` list resolution with named-key delivery, backward-compat shape preserved for single-contract widgets. Fast suite must stay green before any template moves.

### Phase 2 — Retrofit by category

A (model queries) → B (site name) → C (portal auth) → D (admin tools). Per widget: new/extended contract + resolver arm + template rewrite to `$widgetData` + a render-parity test in both data states (populated/empty, logged-in/out). The `LogoGardenContractRetrofitTest` shape is the model.

### Phase 3 — The guard

Write the boundary guard test; it must pass with zero allowlist. Then the rider (decision 6) and the contract-doc update (decision 7).
