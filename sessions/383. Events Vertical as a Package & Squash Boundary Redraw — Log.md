## Production deployment notes

An **existing** deployed database has the three events tables but not the three new migration rows, so a plain `migrate` would try to re-create existing tables and fail. One-time step per environment (the 348/382 squash-class precedent):

- **Disposable data** (demo droplet, auto-deploy server): `docker exec nonprofitcrm_app php artisan migrate:fresh --seed --force`.
- **Data must be kept:** mark the three plugin migrations as applied without running them, then `migrate` behaves normally:

  ```
  docker exec nonprofitcrm_postgres psql -U postgres -d <db> -c \
  "INSERT INTO migrations (migration, batch) SELECT unnest(ARRAY[
     '2026_08_18_000001_create_events_table',
     '2026_08_18_000002_create_ticket_tiers_table',
     '2026_08_18_000003_create_event_registrations_table']),
     (SELECT coalesce(max(batch),0)+1 FROM migrations);"
  ```

Fresh installs need nothing special — dump → plugin migrations → seeders is the normal path. The deploy image requires both plugins' manifest COPY lines (in this branch's Dockerfile). **Bump `VERSION` before any merge-to-main deploy** (done — 0.383.01).
