## Security considerations

The extraction publishes plugin code to a public GitHub repo — owner-created and owner-decided (the code was already MIT-licensed in a public-facing project; no secrets, schema, or client data in the plugin's eight files; verified before push). The public-repo choice is deliberate security-relevant posture: it keeps `composer install` credential-free in every image-building context, avoiding a new token surface in CI/deploy. Guard coverage was deliberately extended so the zero-allowlist scans (template purity, no-admin-CSS, CSP-safe Alpine, SCSS baselines) did not silently shrink when the files left `plugins/` — the alternative failure mode (extracted code exempt from core's contract enforcement) is the quiet one. Supply-chain note: core now depends on a tagged commit of an external repo, pinned in `composer.lock` by exact SHA — a moved tag cannot silently change what installs. No new endpoint, gate, or input path; FM surfaces untouched; CRM contract stays v2.7.0; client-billing guards unaffected.
