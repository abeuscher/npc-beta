## The tier-1 runbook (per-install flag flip)

1. Edit `PLUGINS_DISABLED` in the install's `/opt/nonprofitcrm/.env` (e.g. `PLUGINS_DISABLED=events`; empty enables everything installed).
2. Recreate the containers so the new env is read — `docker compose -f docker-compose.prod.yml up -d` (`.env` is read at container start; the `worker` needs the same restart) — then `php artisan config:clear`.
3. **When enabling** a plugin whose migrations never ran on this install: `php artisan migrate --force` (pending plugin migrations apply then; a previously-run plugin's schema and data are already present and `migrate` is a no-op).

FM's config-push channel is the intended deliverer of step 1; the FM side stays a future FM-contract item (plan § 4d).

## P9 input (what the flag layer / in-repo posture assumes — the extraction must untangle)

1. **Activation is location-independent already**: handles derive from the provider FQCN's namespace, `config/plugins.php` lists FQCNs, and the filter runs before any path is touched — extraction changes nothing here. The 384 generalization test is the standing net that `PLUGINS_DISABLED=logo-garden` keeps working post-extraction.
2. **Path repositories + explicit `version` fields** are the in-repo resolution device; under a VCS repository this inverts — git tags are the metadata, and a retained `version` field becomes an install error on tag mismatch.
3. **Dockerfile per-plugin manifest COPY lines** assume in-repo source paths; a VCS-resolved package needs none (composer fetches it — network/auth posture matters).
4. **Guard globs scan `plugins/*`** (`WidgetTemplateBoundaryTest`, `PluginAdminCssGuardTest`) — an extracted plugin's files leave the scans silently unless the globs extend to the vendor path.
5. **Widget asset paths are repo-relative** (`plugins/LogoGarden/styles.scss`) resolved off disk by `collectSources()`, which **silently skips missing paths** (surface 11's caveat) — the one post-extraction failure a green suite won't catch; the bundle-content check is the gate.
6. **Migration-owning plugins carry `basePath('plugins/…')` reaches** in fixtures (`EventsRemovedTestCase`, `EventsDisabledViaFlagTestCase`) and a phpunit testsuite directory — LogoGarden dodges both, which is part of why it's the P9 subject.
7. **The root `"Plugins\\": "plugins/"` PSR-4 overlap** retires per-plugin as each leaves; after LogoGarden it still covers Payments (+ Events in-repo).

## Security considerations

The activation layer only ever *subtracts* — a flag cannot enable anything not already in the image, and disabling stops provider registration without touching data or schema (normative rule 4, now mechanical). The unknown-handle fail-loud posture is the session's one deliberate security-over-usability call: a silently ignored typo would leave a plugin running that the operator meant to disable. No new endpoint, gate, or input path; the flag is operator-controlled env, not user input. Rider finding: `.dockerignore` widened after the proof build showed locally built images baking in a stray git-ignored `.env.production` (CI/deploy images never affected — clean checkouts); the stale local file is flagged to the owner. FM surfaces untouched; CRM contract stays v2.7.0; client-billing guards unaffected.
