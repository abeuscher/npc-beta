## Process rules for every session

- **Questions are not instructions.** When the user asks a question, the correct response is an *answer*, then a wait. Do not read a question as a veiled directive to act. Heuristic: *if you can answer in words and stop, do that; only act on an explicit instruction.*
- **Human-facing output follows the reporting rules in `CLAUDE.md`.** That governs the Open Gate orientation, the classification-table digest, the completion report, and the session log. The dense process register here is how you *operate*, not how you *report*. Switch registers at those boundaries.
- **Before writing any code**, read every file you intend to modify.
- **Pause and ask** any time a decision point arises that the agreed prompt doesn't cover. See the drift and decision-threshold rules below.
- **Surface architectural choices before going deep.** Two are named in the session prompt's Open Questions and both are genuinely the user's: whether the track gains a D5 plugin-boundary dimension, and whether the `nav is not defined` regression is fixed inside an audit session. Diagnose both fully, then surface with a recommendation. Do not commit to either and unwind later.
- **Adapt to drift; don't ask about it.** The session prompt's survey is a snapshot taken at drafting. Expect inaccuracies in spec counts, line numbers, and grep tallies. Default to adapting silently and noting the adaptation in one line in your work log. Flag drift only when it needs a decision: two readings produce meaningfully different work, the drift reveals a likely bug, resolving it expands scope, or you can't tell whether to build or to treat it as a misread. Heuristic: *fix vs. decide — if you can resolve it by editing your own output without changing the system's intent, just fix it.*
- **Decision threshold scales with project maturity.** This project is well past its loose phase. Reserve "pause and ask" for decisions expensive to reverse — a deletion policy that propagates, a contract clause, anything cross-cutting. For local calls with an obvious answer given surrounding code (naming, file placement, which helper to use), decide and note it.
- **Deletions need evidence, not vibes.** This is a delete-leaning session by the track's design, and every deletion carries a one-line rationale tied to something observed — a Pest test that covers the path, a CI history showing the spec never ran, a title that overclaims its body.
