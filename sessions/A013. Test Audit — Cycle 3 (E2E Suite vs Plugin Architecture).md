## Open questions to resolve at session start

Settle these before Phase 3 applies anything. Two need the user; the rest resolve on evidence.

- **Does the Test Audit track gain a fifth dimension — D5, plugin-boundary spec ownership?** The track doc defines exactly four dimensions and the plugin architecture postdates all of them. The question this cycle must answer is *where a browser spec lives once its vertical is a package*: (a) it travels to the plugin repo alongside the Pest suite, and the plugin contract gains an e2e clause; (b) it stays in core, because e2e asserts the assembled application and only the assembled application has a browser; (c) per-spec, on whether the assertion is about the vertical or about core chrome hosting it. **This is architectural and propagates to every future extraction — surface it to the user with a recommendation before applying any disposition that depends on it.** Note the hard constraint below: whichever answer wins, this session decides the policy and writes it down; it does not execute a cross-repo migration.
- **Is the `nav is not defined` chrome-parity failure fixed here?** Audit discipline (Cycle 1 and 2 both) is test-code and docs only, no application code. But this is a live regression on `main` that nobody else is watching, and leaving it red leaves the whole job red — which is the condition that let it merge unnoticed in the first place. Diagnose it either way; **surface the fix/defer call to the user with the root cause in hand**, per A007's decision-tree (c) and the base prompt's "surface architectural choices" rule.
- **What is the policy for a test that skips itself in CI?** The A005 precedent is delete-by-default; the A011 precedent is gate-and-record-the-tradeoff. Both are live in the current suite. The `public-console-errors.spec.ts` case is the forcing one — a spec whose every test skips in CI is indistinguishable from an absent spec, but the *local* stack does build the bundle, so it is not worthless. Options: delete, keep gated with the tradeoff recorded, or split the bundle-dependent assertions from the ones that hold without it. Decide per-spec on evidence; record the rule so the next author isn't guessing.
- **Do the orphaned fixture sets go?** Almost certainly yes, but check that `helpers/wizard.ts` / `helpers/db.ts` don't need their map entries for the generator (`GenerateImportFixtures`) or for a Pest consumer before deleting the CSV/JSON.
- **Is there a shared cause behind the skips and the red?** A007 looked for a uniform signature and correctly found none. Look again with fresh evidence; be equally ready to find that the residuals are unrelated.

## Phases

### Phase 1 — Evidence and inventory

No fixes in this phase. Two deliverables:

- **The CI evidence.** Pull the current Playwright job log via `mcp__github__get_job_logs` — the failure, the flake, the skip list, per-spec timings. Then walk the job's *history* far enough back to answer, for each spec that looks suspicious: has this ever been green in CI, and when did it last change state? That history is what separates a real regression from a spec that never ran. The chrome-parity `nav is not defined` failure gets root-caused here — find what `nav` is and which change dropped it — but not fixed.
- **The inventory.** All 28 specs, one row each: what its assertions actually test, whether the surface is browser-required, whether the surface is core-owned or plugin-owned, whether its title matches its body, whether it skips in CI and under what condition. Build it from reading the specs, not from this prompt's survey — the survey is a starting map and will have drifted.

### Phase 2 — Classify

Per spec, a verdict on each dimension in play:

- **D1** — Keep (browser-required) / Redundant (data covered by Pest) / Mixed (split or rewrite), per `docs/testing/playwright-discipline.md`. The FixtureRunner-is-the-safety-net rule gates every Redundant verdict on an importer spec: confirm `tests/Feature/Generated/ImportFixtureRunnerTest.php` or a namespaced Feature test actually covers the path before deleting.
- **D2** — does the title match the body? Default lean is rename-to-match, not expand-the-test.
- **D5 (if blessed)** — core-owned / plugin-owned / boundary-ambiguous, and the disposition that follows from the policy the user picks.

**Surface the classification table to the user before applying anything.** That is the Cycle-1 and Cycle-2 pattern and it is not optional — the reductions are the point of the session, and a wrong delete is expensive to notice.

### Phase 3 — Apply

One commit per coherent class. Per the track's delete-leaning posture, every deletion carries a one-line rationale tied to evidence, and every disposition lands a `[test-integrity]` line in `sessions/housekeeping-inbox.md` naming what went and what coverage was traded away.

- Deletions and rewrites per the blessed verdicts.
- Any spec rewritten more than trivially is authored to `docs/testing/playwright-discipline.md` — and note the local-first clause cannot be honoured in this environment (no Docker, no Playwright install), so CI is the authoring signal this once; say so in the log rather than implying the discipline was followed.
- The chrome-parity disposition, per the user's call.
- Orphaned fixture disposal.

Verify with one CI run: `rc=0`, no `unexpected`. A retry-recovered `flaky` is acceptable under the standard `retries: 1` model.

If D5 concludes that specs travel, this session writes the policy, the contract clause and the runbook step — a later session (or the next extraction, 397's Forms carve) performs the first migration. Do not attach sibling repos to work around this without asking.
- **Reverting or re-litigating the plugin architecture.** Seven extractions are shipped product decisions. If a spec asserts on a surface that moved, the spec adapts.
- **Adding a build server to the e2e stack.** The recorded posture is no external build pipeline in CI. A spec that needs the runtime widget bundle is a disposition question, not a licence to add `bundleserver` infra.
- **Re-quarantining.** A `QUARANTINED_SPECS` list or its equivalent is forbidden — the original stabilization deleted that pattern permanently. `describe.skip` only when a test still has value and is provably environment-blocked, and even then prefer deletion-with-a-housekeeping-note.

## Testing

- **Primary signal:** the `Playwright e2e (isolated stack)` job concluding `success` on the pushed branch — `rc=0`, no `unexpected`. Retry-recovered `flaky` is acceptable.
- **Secondary signal:** the aggregate `Tests` check (fast + slow Pest) stays green. If a fixture or registry deletion touches a Pest consumer, that check is the proof.
- **Slow Pest groups to run:** none expected. If a product fix lands, run the groups it touches — via CI, given the cloud constraint.
- **New tests expected:** deletions and rewrites, yes; net-new specs, no (see Out of scope). Pest additions only if a product fix lands that warrants one.
- **Environment constraint:** no Docker daemon, no `node_modules`, no `vendor` in the agent's environment. `./dev test` and `npm run test:e2e` are both unavailable. CI is the only execution channel, and `mcp__github__get_job_logs` is the read channel.
