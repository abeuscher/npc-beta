## The survey (ground truth, captured at 384 close)

**The subject:** `plugins/LogoGarden/` — eight files, no schema, no migrations, no routes, no admin pages, no in-plugin tests: `LogoGardenServiceProvider` (registers the widget definition + Blade namespace), `LogoGardenDefinition` (declares repo-relative assets: `plugins/LogoGarden/styles.scss`, `plugins/LogoGarden/script.js`, lib `swiper`), `template.blade.php`, `DemoSeeder`, `thumbnails/`, `composer.json` (`nonprofitcrm/logo-garden`, `"type": "library"`, explicit `"version": "0.1.0"`, PSR-4 `Plugins\LogoGarden\` → `""`, PHP `^8.2` only, MIT license already declared).

**How core consumes it today:** root `composer.json` carries a `path` repository entry for `plugins/LogoGarden` + a bound `"nonprofitcrm/logo-garden": "^0.1"` require; `composer install` symlinks `vendor/nonprofitcrm/logo-garden` → the folder. The explicit `version` field exists because path repos resolve without git metadata (the P6 determinism rationale) — under a VCS repository this inverts: **git tags are the version metadata**, and an explicit `version` field in a tagged repo is a foot-gun (composer errors on tag/field mismatch). The Dockerfile copies the manifest before both `composer install` layers (two COPY lines).

**What is location-independent already (P8 verified):** activation. `config/plugins.php` lists the provider FQCN; the P8 handle derivation reads the namespace, not the path; `PLUGINS_DISABLED=logo-garden` and the remove-the-line guarantee work identically wherever the class autoloads from. Nothing in the activation layer changes this session.

**What is location-keyed and breaks on extraction (the 384 P9-input inventory, LogoGarden slice):**

1. **Asset paths** — `assets()` declares `plugins/LogoGarden/…`; `AssetBuildService::collectSources()` resolves via `base_path()` off disk and **silently skips missing paths** (surface 11's caveat) — the one failure mode here that a green suite won't catch.
2. **Guard globs** — `WidgetTemplateBoundaryTest` scans `plugins/*/template.blade.php`; `PluginAdminCssGuardTest` scans `plugins/`. An extracted plugin's files leave the scan silently.
3. **`PluginPackageGuardTest`** — asserts every plugin package is lock-pinned with `dist.type = path`; the extracted package's dist type changes.
4. **Dockerfile manifest COPY lines** — a VCS-resolved package needs no source COPY at all; composer fetches it (network + auth reach the build).
5. **Thumbnails** — `scripts/generate-thumbnails.js` writes to `app/Widgets/{Name}/` or `plugins/{Name}/`; the vendor'd plugin ships its thumbnails in its own repo (already generated — no regeneration needed this session), and `thumbnailDir()` resolves by reflection, so serving keeps working from the vendor path.
6. **Root PSR-4 overlap** — `"Plugins\\": "plugins/"` stays (Payments and Events still live there), but it no longer covers LogoGarden; the package's own PSR-4 is the only mapping. The contract's "retires per-plugin" line becomes real for the first time.

**What LogoGarden deliberately dodges** (why it's the subject): no migrations (no `basePath('plugins/…/database/migrations')` fixture reaches), no phpunit testsuite directory of its own, no cross-plugin asset input (that's EventsListing→BlogPager, an Events problem, flagged at 382 for whenever Events extracts).

**Tests with LogoGarden as subject, all currently core:** `PluginPilotSession377Test` (registration, sync row, view namespace, asset paths exist on disk), `LogoGardenContractRetrofitTest` (render parity through the resolver), `LogoGardenWidgetTest`. Under normative rule 5's membership rule these are plugin-subject tests; but they are also core's *pilot* proofs, written against the loader. **Settled (owner ruling, 384 close): they stay core this round** — see decision 8.

**The target repo (owner-created at 384 close, verified):** `https://github.com/abeuscher/crm-plugin--logo-garden.git`, checked out locally at `../crm-plugin--logo-garden` (sibling of this repo). Empty — no commits yet, default branch `main`, remote wired. **Public**, so `composer install` stays credential-free in every context that builds the image (CI tests job, CI e2e image build, GHCR deploy build, a fresh machine). The naming pattern `crm-plugin--{kebab-handle}` is the precedent future extractions follow.

**The FM-relationship discipline being mirrored:** separate repo, tagged versions, a contract doc both sides program against (`docs/plugin-contract.md` is the contract; the plugin repo pins which version it implements), changes land contract-first.

## Front-loaded decisions (settled at 384 prompt-draft time — reviewed with this prompt; do not reopen in session)

1. **LogoGarden is the extraction subject.** Smallest surface, zero schema/routes/admin, and it exercises the one genuinely hard cross-repo seam — widget assets built off-disk paths — without dragging migrations or testsuite mechanics along. Events and Payments wait for the runbook.
2. **Consumption mechanics: composer VCS repository + git tag.** The plugin's files land at the root of the owner-created repo (`abeuscher/crm-plugin--logo-garden`, empty and public — see the survey; composer.json at top level); root `composer.json` swaps the path entry for a `vcs` repository entry pointing at the GitHub URL; the require stays bound (`^0.1`); the extracted repo drops the explicit `version` field and tags `v0.1.0` instead (the field is a path-repo determinism device; in a VCS repo the tag is canonical and a mismatched field is an install error). Lockfile updated; `composer validate --strict` clean; the Dockerfile's two LogoGarden manifest COPY lines are removed (composer fetches the package; no source COPY).
3. **Asset paths become vendor-relative repo paths** in `assets()`: `vendor/nonprofitcrm/logo-garden/styles.scss` etc. — the mechanically smallest change; `AssetBuildService` and `widgets:sync` are untouched (paths are opaque repo-relative strings to them). The verification gate is explicit: `widgets:sync` → `build:public` → assert the manifest and built bundle carry LogoGarden's content (surface 11's silent-skip caveat is the risk this gate exists for). A `baseDir()`-derived declaration (paths computed by reflection) is noted as a cleaner future shape but NOT built — it changes every plugin's contract surface for one consumer's benefit; backlog line.
4. **Core keeps enforcing the contract on what it composes: guard globs extend to the vendor path.** `WidgetTemplateBoundaryTest` and `PluginAdminCssGuardTest` add `vendor/nonprofitcrm/*/…` globs alongside `plugins/*` — the zero-allowlist guarantees must not silently shrink when a plugin leaves the repo. `PluginPackageGuardTest` updates: the extracted package is lock-pinned with a VCS/dist source (exact assertion per what the lockfile records) and still declares no auto-discovery; in-repo packages keep the `path` assertion.
5. **Repo hygiene mirrors FM:** the new repo gets a README stating what it is, which plugin-contract version it implements (0.9.0 at close), and the tag discipline (tags are releases; core bumps its require deliberately). No CI in the plugin repo this session (tests stay core per decision 8) — the runbook records per-plugin CI as the standing follow-up.
6. **The runbook is `docs/plugin-extraction-runbook.md`:** the generic numbered procedure — preconditions (plugin is already a Stage B package; tests green), the repo-creation step, the file move with history note, the composer swap (repository entry, version-field drop, tag, lock update, strict validate), the Dockerfile cleanup, the asset-path rewrite + bundle verification gate, the guard-glob extension, the test-membership decision point, the in-image proof, and the full verification gate list (fast suite, route parity, bundle content, fresh-install identity, CI incl. the image-building e2e job). LogoGarden appears as the worked example under each step.
7. **Contract doc at close:** Package shape section gains the **External repo (Stage C)** subsection (VCS repository + tags; version-field inversion; the public-repo/credential-free posture; what stays identical — provider entry point, config-list activation, namespace-keyed handles); surface 11 gains the vendor-path note + the verification gate; bump 0.8.0 → 0.9.0, changelog entry. Not boundary-touching (no FM surface).
8. **The three LogoGarden-subject test files stay core this round** *(owner ruling, 384 close)*. Rule 5's target posture (plugin-subject tests ship with the plugin) would mean standing up per-plugin CI in the new repo this session — these tests boot the full Laravel app, so they'd need core as a dev dependency, non-trivial plumbing. Recorded as accepted debt in the runbook's test-membership step; the runbook documents the target posture (disposition 3: the central build runs core + the distribution's plugin suites — P10's concern) rather than half-building it here.
