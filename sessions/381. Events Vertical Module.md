- Seven widgets: `EventDescription`, `EventImage`, `EventMiniCalendar` (js+scss+`event-row` partial), `EventRegistration` (js), `EventsListing` (js+scss+`row` partial), `PortalEventRegistrations`, `ThisWeeksEvents`. - Importers: `EventFieldRegistry`, `EventImportFieldRegistry`, `RegistrationFieldRegistry` + `ImportEventsPage` / `ImportEventsProgressPage`. Core consumers that must NOT reach the plugin afterwards: `CsvTemplateService`, `ImportSessionActions`, `ImportSessionPreview`, `SeedFakeImportSourcesCommand` — hence the importer socket (decision 4). `AggregatingRegistry` (the base) stays core; `TransactionFieldRegistry` (core, cross-references registration data) stays core.
- Routes: `events.register` (POST, throttle:10,1), `portal.events.register` (POST, portal-auth stack), `api.events.json` (GET closure feeding the calendar widget — moves verbatim; it reads the core Event model, which is fine from the plugin).

**The Payments seam (inverts):** `plugins/Payments/Http/Controllers/StripeWebhookController::handleEventRegistrationCheckout` — promotion of pending registrations by `stripe_session_id`, one `Transaction::recordStripe`, one queued `RegistrationConfirmation`, idempotent via the pending-only filter. If the mail class moves to `plugins/Events/` while this handler stays, Payments would reference `Plugins\Events\` — a forbidden foundation→vertical reach. That is exactly the trigger the P4 contract note named; the inversion is due now (decision 5).

**What stays core (the deliberate Stage-A line — models are core, so these are legitimate core code, not violations):** the three models `Event` / `EventRegistration` / `TicketTier` and their tables/migrations (annotated as events-owned, moving at P7 with the squash redraw); the `ContractResolver` / `SystemModelProjector` event arms; `PageBuilderDataSources`; content import/export (`EventSerializer`, `EventImporter`, `ContentExporter/Importer`); `RandomDataGenerator`; `SeoMetaGenerator`; `CmsFormFields`; `SanitisesRichTextCustomFields`; `MediaReferenceInventory`; the `Contact` / `Organization` event relations; `TransactionResource`'s registration references; the `Page` model and landing-page rendering (pages are core CMS).

**Permissions (behavior-preserving wrinkle):** the `event` resource permissions are generated from `PermissionSeeder`'s core resource list and granted to shipped roles (`event_manager`, board read-only, etc.). They are NOT new plugin permissions — moving their seeding to the plugin's `AdminContribution` channel would break the role matrix on a plugin-removed install (Spatie throws granting a missing permission). They stay core-seeded (decision 6).

**Vanish shape (verify, don't assume):** with the Events line removed — POST register routes answer 405 (the page catch-all owns GET on every path, the 380 precedent), `api/events.json` falls to the page catch-all as a 404, admin event pages and the importer are gone, no reminders job is scheduled, `widgets:sync` drops the seven `widget_types` rows, event landing pages still render (missing widget types are skipped by the public renderer — verify), and a late Stripe webhook for an events session dispatches the typed event to no listener and returns 200 with rows left pending — data kept, writes stopped.

## Front-loaded decisions (settled at 380 prompt-draft time — do not reopen in session)

1. **Module shape:** `plugins/Events/`, namespace `Plugins\Events\`, provider `EventsServiceProvider` listed in `config/plugins.php` after Payments. Internal folder layout is the session's call (log it). The provider owns: route file(s) (web-group parity, the Payments precedent), both observer registrations, `Gate::policy(Event::class, EventPolicy::class)`, command registration + schedule (`events:send-reminders`, registered from the provider so removal unschedules it), widget definition registrations + Blade namespace(s), the `AdminContribution` (discovery paths for the resource + import pages), and the importer contribution (decision 4).
2. **Models and schema stay core at P5.** `Event`, `EventRegistration`, `TicketTier`, their migrations, factories, and the engine seams that read them (survey list) do not move. Deliverable in lieu: an "events-owned schema" annotation (tables + migration list) recorded in the plan doc § 6.7 area, the input for P6/P7's squash redraw. Plugin→core model reaches are the allowed hard dependency; the one-directional guard (decision 7) is what makes the boundary real.
3. **Admin socket goes real (surfaces 3/4 → PROVEN).** `EventResource` + four pages move under the plugin and register via `AdminContribution` discovery paths — nav group unchanged (core group list, Filament-native `$navigationGroup` naming an existing group), sort weight preserved, no plugin admin CSS (`PluginAdminCssGuardTest` already stands). The registrant export and cancellation wizard move intact. If the resource needs an in-panel route pull, it rides the `routesFile` mechanism (force-wrapped in `Authenticate` by core).
4. **Importer socket (surface 8 mechanics), mirroring the 379/380 registry pattern:** a core-owned importer registry singleton bound in `PluginServiceProvider`; plugins contribute their field-registry classes + import-page pairing at `register()`; the core consumers (`CsvTemplateService`, `ImportSessionActions`, `ImportSessionPreview`, `SeedFakeImportSourcesCommand`) resolve through it instead of naming the classes. Core-owned importers (contacts, donations, memberships, invoices, notes, organizations, transactions) stay hard-wired or join the same registry as core entries — session's call, log it; the socket's shape must serve both.
5. **The inbound inversion (surface 10, events slice).** A core-owned typed event — working name `App\Payments\Events\CheckoutSettled`, final name the session's call — carrying the Stripe session object + metadata. The Payments webhook keeps the metadata routing switch (the metadata key is written by the vertical at session creation; routing is payments infrastructure), but the `event_registration_checkout` branch body becomes: dispatch the typed event, return 200. The Events plugin's listener owns the entire former handler behavior — pending-promotion by `stripe_session_id`, `Transaction::recordStripe` (a core write, allowed), the queued `RegistrationConfirmation` — with idempotency semantics identical (pending-only filter; replay finds nothing pending). Donation, membership, product, generic-fallback, invoice, refund, and failed-intent handling stay inline in Payments — they invert per-vertical as each extracts. With Events absent, the dispatch has no listener: 200, rows stay pending, data kept.
6. **Permissions stay core-seeded.** The `event` resource permission names remain in `PermissionSeeder`'s core matrix with their existing shipped-role grants — zero grant changes, zero seeding changes. The surface-3 "plugin declares permissions, granted to no shipped role" channel is for genuinely NEW permission names; an extracted vertical's pre-existing permissions are part of core's role matrix until the matrix itself becomes composable (P8 territory at the earliest). Record this nuance in the contract doc's surface 3 entry at close.
7. **Standing guard: `EventModuleBoundaryTest`.** Bans `Plugins\Events\` references anywhere in `app/` (all `.php` including Blade), zero allowlist, with a positive control on `config/plugins.php` — the `PaymentModuleBoundaryTest` pattern minus the SDK bans (no third-party SDK in this vertical). `PaymentModuleBoundaryTest` and `ConventionDriftTest` must remain green untouched; `WidgetTemplateBoundaryTest` already scans `plugins/*` template paths — verify its glob catches the moved widget templates' actual layout (subfolder shape is the session's call; extend the glob in the same commit if the layout requires it, that is not an allowlist change).
8. **The Events×Payments presence matrix is tested explicitly.** (a) Both present: the existing suite. (b) Events present, Payments removed (`PaymentsRemovedTestCase`, exists since 380): free and comp registration work, paid registration returns the existing not-configured error — the "Events without Payments = free events only" claim as executable tests. (c) Events removed (new `EventsRemovedTestCase`, the 380 strip-the-line mechanism): the vanish shape from the survey, plus the free paths of OTHER surfaces unaffected. Twin file on the plain TestCase mirrors what must be present.
9. **Riders:** (a) the absorbed inbox backfill — one Mail-faked test exercising `EditEvent`'s live cancellation-wizard send, landing with the page move; (b) the events-owned-schema annotation (decision 2). **Backlog lines (not this session):** the EventController↔Portal paid-branch duplication (pre-existing), per-plugin test suites (P7), the events e2e coverage gap, resolver-arm contribution mechanics for plugin-owned models (needed no earlier than P7, when models move).
10. **Contract doc at close (0.4.0 → 0.5.0):** surfaces 3 and 4 → PROVEN (first shipping admin-page plugin, the 379 fixture retired or kept as regression fixture — session's call); surface 8 recorded with the socket mechanics → PROVEN if the shipping importer exercises it end-to-end (it does, per the honesty rule); surface 10 recorded with the typed-event mechanics → PROVEN scoped to the events slice, with the per-vertical rollout note; surface 2 notes the at-scale contributor (7 widgets, partials + assets); surface 13 notes the first vertical consuming a capability from inside a plugin; surface 3 gains the extracted-vertical permission nuance (decision 6). Changelog entry.
