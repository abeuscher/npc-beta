## Production deployment notes

An **existing** deployed database has the four product tables but not the four new migration rows, so a plain `migrate` would try to re-create existing tables and fail. One-time step per environment (the 390/393/395/397 precedent; the local dev database was walked this way in-session):

- **Disposable data** (demo droplet, auto-deploy server): `docker exec nonprofitcrm_app php artisan migrate:fresh --seed --force`.
- **Data must be kept:** mark the four plugin migrations as applied, then `migrate` behaves normally (it will also run the allocations drop):

  ```
  docker exec nonprofitcrm_postgres psql -U postgres -d <db> -c \
  "INSERT INTO migrations (migration, batch) SELECT unnest(ARRAY[
     '2026_08_20_300001_create_products_table',
     '2026_08_20_300002_create_product_prices_table',
     '2026_08_20_300003_create_purchases_table',
     '2026_08_20_300004_create_waitlist_entries_table']),
     (SELECT coalesce(max(batch),0)+1 FROM migrations);"
  ```

Fresh installs need nothing special. The deploy image build now fetches `nonprofitcrm/products` v0.1.0 and `nonprofitcrm/payments` v0.4.0 from GitHub (public, credential-free) — no pipeline change. Deploy already runs `widgets:sync` + `build:public`, which picks up the vendor-relative carousel paths (verified locally; handles unchanged). VERSION bumped 0.397.01 → **0.398.01**.
