## Production deployment notes

An **existing** deployed database has the two membership tables but not the two new migration rows, so a plain `migrate` would try to re-create existing tables and fail. One-time step per environment (the 390 precedent):

- **Disposable data** (demo droplet, auto-deploy server): `docker exec nonprofitcrm_app php artisan migrate:fresh --seed --force`.
- **Data must be kept:** mark the two plugin migrations as applied, then `migrate` behaves normally:

  ```
  docker exec nonprofitcrm_postgres psql -U postgres -d <db> -c \
  "INSERT INTO migrations (migration, batch) SELECT unnest(ARRAY[
     '2026_08_20_000001_create_membership_tiers_table',
     '2026_08_20_000002_create_memberships_table']),
     (SELECT coalesce(max(batch),0)+1 FROM migrations);"
  ```

Fresh installs need nothing special. The deploy image build now fetches `nonprofitcrm/memberships` from GitHub (public, credential-free) — no pipeline change (the standing precedent held). Deploy already runs `widgets:sync` + `build:public`, which picks up the vendor-relative PricingChart path (verified locally). VERSION bumped 0.392.01 → **0.393.01**.
