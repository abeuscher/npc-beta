## The survey (ground truth, captured at 385 close)

**What the root repo hardcodes about the plugin set today** (the 385 P10 input, verified):

1. **`config/plugins.php`** — the ordered provider-FQCN list; the installed superset + sole ordering authority (contract surface 1). Hand-edited.
2. **Root `composer.json`** — one repository entry per packaged plugin (path for in-repo Events; vcs for external LogoGarden) + one bound require line each. Payments has neither (still a plain folder on the root `"Plugins\\"` PSR-4).
3. **`Dockerfile`** — one manifest COPY line per *in-repo* packaged plugin, ×2 composer stages (currently: Events only; LogoGarden's lines left at P9).
4. **Guard lists** — `PluginPackageGuardTest`'s `EXTRACTED_PLUGIN_PACKAGES` const; the same test's glob over `plugins/*/composer.json` for path-pinning.
5. **`phpunit.xml`** — the `Events` testsuite directory (a per-plugin test location the manifest does not need to own, but should be derivable-from or at least consistent-with).

**What already behaves manifest-like:** `config/plugins.php` was designed as "the in-repo miniature of the future distribution-manifest layer" (contract surface 1, verbatim since 0.1.0). P10 completes that sentence: the miniature becomes the derived artifact of the real thing.

**The FM-facing surface P10 must NOT change:** `deploy.yml`'s observable behavior — GHCR image names, the immutable-VERSION tag enforcement, what `/api/health` reports, the VERSION file semantics. The plugin-manifest-in-health-payload item stays future FM-contract work (plan § 4d; Two-Repo Coordination Protocol). P10 is **non-boundary by design**; if implementation discovers an FM-visible change is genuinely needed, that is a pause-and-ask, not a decide-and-log.

## Front-loaded decisions (drafted at 385 close — review at prompt review; reopen only what the Open Gate flags)

1. **The manifest is `distribution.json` at the repo root** — one file, the default distribution ("this repo's composition"). Per plugin entry: composer package name, the provider FQCN, the source kind (`path` / `vcs` + URL), and the bound version constraint. **Order is meaning** — the array order is the provider load order (the ordering authority moves here). Separate per-niche distribution repos are Stage E; P10 builds the layer with one distribution.
2. **`config/plugins.php` becomes a generated artifact** — a small artisan command (`plugins:manifest-sync` or similar) writes it from the manifest, preserving order; the file stays committed (the runtime loader still reads it; no bootstrap-time JSON parsing) and gains a generated-file header. **Remove-the-entry ≡ remove-the-line by construction** — the same guarantee, one level up. `PluginServiceProvider`, the activation layer, and every existing test are untouched.
3. **Guards pin the alignment, not generation everywhere:** a new standing guard asserts (a) regenerating from the manifest reproduces the committed `config/plugins.php` byte-identically (staleness fails), (b) every manifest entry is lock-pinned in `composer.lock` with the source kind the manifest declares, (c) every `nonprofitcrm/*` package in the lock appears in the manifest (no unmanifested plugins), and (d) `EXTRACTED_PLUGIN_PACKAGES` matches the manifest's vcs-sourced set (or the const is replaced by a manifest read — implementer's call, log it). `composer.json` and the Dockerfile stay hand-maintained and guard-verified, NOT generated — generating composer.json wholesale is invasive machinery for zero current benefit; the guard makes drift loud instead.
4. **Payments joins the manifest as-is** (a `Plugins\` PSR-4 folder entry with no composer package — the manifest models the real current state honestly; its packaging is Stage D position D1, not this session). If modeling the unpackaged state proves ugly, packaging Payments here is explicitly NOT the fix — model it or note it, D1 owns the packaging.
5. **The central-build proof is a verified run, superset-image style:** (a) build the image from the manifest as committed → byte-identical composition (routes 272, migrations 117, `widgets:sync` 41, suite untouched); (b) on a scratch branch/working tree, remove the Events entry from the manifest, regenerate, rebuild → the image composes without Events (migrations 114, widgets 34, routes/schedule gone — the 384 proof's assertions, now driven by a manifest edit and nothing else); (c) restore. **Scope note:** at P10 a manifest edit changes what *registers/migrates/syncs*; the package code may still ship in the image (inert). True per-distribution code absence (tier-2's "not in the niche image") arrives with Stage E's per-distribution composer sets — record this boundary in the contract doc, don't build it.
6. **`deploy.yml` / CI:** expected touch is minimal-to-none (the manifest guard runs inside the Pest suite; the image build already re-proves composer resolution). Any touch must leave FM-facing behavior byte-identical — state the diff explicitly in the log.
7. **Contract doc at close: 0.9.0 → 0.10.0.** Surface 1 amended (installed = the distribution manifest's set; `config/plugins.php` generated, ordering preserved, remove-the-entry guarantee); Package shape gains the distribution-manifest layer; the Stage E boundary (per-distribution composer sets) recorded as future work. Runbook updated: extraction step list gains "add/update the plugin's manifest entry" and drops what the manifest now derives.
8. **No new third-party dependencies** (no composer merge-plugins, no schema libs — plain JSON + a command + Pest).
