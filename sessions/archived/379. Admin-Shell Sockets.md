## The survey (ground truth, captured at 378 close)

`AdminPanelProvider::panel()` (538 lines) carries a ~100-line inline `->routes()` closure with ten feature clusters:

1. Two-factor setup + challenge pages (deliberately outside `authMiddleware` — the no-redirect-loop comment is load-bearing, preserve it with the routes)
2. Invitation show/store
3. Inline image upload (demo-upload gate) + media dedup check + heroicons index
4. QuickBooks OAuth connect/callback/disconnect
5. Page-builder API → `routes/admin-api.php`
6. Dashboard-builder API → `routes/admin-dashboard-api.php`
7. Record-detail-view-builder API → `routes/admin-record-detail-view-api.php`
8. Theme editor (typography update/export/rebuild)
9. Dev-tools (random-data store/wipe/seed-collections)
10. Setup-checklist actions + the bundle-export download route

Everything else in the provider (render hooks, middleware stacks, brand block, nav groups, discovery calls) is **out of scope** — it stays exactly where it is.

Nav conventions today: Filament-native `$navigationGroup` strings + `$navigationSort` ints on resources/pages; the five core groups (CRM / CMS / Finance / Tools / Settings) are declared in the provider's `->navigationGroups()`. Permissions today: `PermissionSeeder` builds core's vocabulary; the `manage_account` precedent is seeded-but-granted-to-no-shipped-role. `PluginServiceProvider` registers plugin providers from `config/plugins.php` in `register()`.

## Front-loaded decisions (settled at 378 prompt-draft time — do not reopen in session)

1. **Route files live under `routes/admin/`, one per feature cluster.** New files: `two-factor.php`, `invitations.php`, `media.php` (upload + dedup + heroicons), `quickbooks.php`, `theme.php`, `dev-tools.php`, `setup-checklist.php`, `exports.php`. The three existing builder API files **move** into `routes/admin/` (`git mv`, names preserved: `builder-page.php`, `builder-dashboard.php`, `builder-record-detail.php` — or keep their current basenames if any tooling references them; session's call, log it). The `->routes()` closure shrinks to a loop/list of `Route::…->group(base_path('routes/admin/…'))` pulls. Route **names, URIs, methods, and middleware are unchanged** — parity proven by a before/after `route:list --json` diff recorded in the work log. Load-bearing comments (2FA loop-avoidance, demo-upload gate, CB-suspension notes) travel with their routes.
2. **The plugin admin socket is a core registry consumed by the panel provider.** Plugin providers declare admin contributions at `register()` time into a core-owned registry (shape: Filament discovery paths for resources/pages, an in-panel route file path, and declared permissions). `AdminPanelProvider::panel()` reads the registry when Filament builds the panel — plugin providers register before panels build via `bootstrap/providers.php` ordering; **verify this ordering in-session and, if it bites, fall back to reading `config/plugins.php`-declared classes directly**. Exact registry shape (dedicated class vs. statics on `PluginServiceProvider`) is the session's call; the declared surface (paths + route file + permissions + nav group/sort) is settled per contract surface 3.
3. **Nav convention:** core owns the group list (the five `->navigationGroups()` entries stay in the provider, the single source). Plugin pages join a group by declaring Filament-native `$navigationGroup` (must match a core group — no plugin-invented groups in Stage A) and order themselves with `$navigationSort`. No new mechanism needed beyond the registry's discovery paths; the rule is recorded in the contract doc.
4. **Permission convention:** a plugin declares its permission names in its registry entry; a core sync step seeds them `firstOrCreate` (guard `web`) when the plugin is enabled — Stage A "enabled" = listed in `config/plugins.php`, so seeding runs wherever core permission seeding runs today plus an idempotent registry sweep (mechanism — extend `PermissionSeeder` to sweep the registry, or a `plugins:sync` step — session's call, log it). Seeded permissions are granted to **no shipped role**; super-admin passes via the existing gate bypass (the `manage_account` precedent). Disabled plugin = permissions remain but gate nothing (disabled-is-inert normative rule; no deletion).
5. **Core-owned admin theme:** plugins ship no admin CSS. Enforced, not just documented: extend the standing-guard pattern with a case that fails if `plugins/*` contains admin-surface CSS or a `viteTheme`/render-hook stylesheet contribution (exact detection — glob for `admin*.css` / scan providers for `viteTheme(` — session's call). Widget-scoped SCSS under `plugins/*` (the LogoGarden precedent, built by `build:public`) remains legitimate and must not trip the guard.
6. **The socket is proven by a test-fixture plugin, not a shipped one.** A minimal fixture (e.g. `tests/Fixtures/Plugins/SocketProbe/…`, registered only inside tests) declares one Filament page in a core nav group with a sort weight, one route file, and one permission; tests assert the page is discoverable, the route registers with panel middleware, the permission seeds idempotently and is granted to no role, and removing the plugin from the config list makes all of it vanish (the surface-1 remove-the-line guarantee extended to the admin socket). Fixture-tested ≠ PROVEN: surfaces 3/4 stay DECLARED in the doc with the mechanics + test named.
7. **Contract doc at close:** surfaces 3 and 4 updated with the concrete mechanics (registry shape, `routes/admin/` layout, conventions 3–5), status DECLARED kept, fixture test named; version bump + changelog per the doc's discipline.
