## What "RimWorld-like" means — unpack this FIRST, with the owner

RimWorld's mod architecture has several distinct properties, and which ones the owner actually prizes determines everything downstream. Open the discussion by walking these and asking which are the point and which are incidental:

1. **Minimal core, maximal periphery** — the base game is an engine + core defs; almost every feature is structurally a mod, including first-party content ("everything is a mod, even the core").
2. **Declarative definitions** — mods are mostly *data* (XML defs) that the engine interprets; code is the exception, not the rule. (The widget system's `config_schema` + definition classes already rhyme with this.)
3. **Separate distribution** — mods live outside the core's repo/filesystem, versioned independently.
4. **Load order + patching** — mods can extend and *modify* each other and core content, with deterministic ordering and conflict surfacing.
5. **Per-install composition** — an installation chooses its mod set; enable/disable without rebuilding the world.
6. **Community authorship** — third parties can write mods against a stable, documented modding API.

Likely read (verify, don't assume): the owner's phrasing — "separate repos with a central build" — leans on #1 and #3, with #5 as the operational payoff (a nonprofit's install runs only the plugins it needs). #6 is probably aspirational; #4 is where cost explodes and may be explicitly out. Getting this ranking from the owner **is the first hour of the session.**

## Discussion agenda

### Phase 1 — The inventory: what is already plugin-shaped

Present the code reality (read during the base-prompt list, summarized in plain language):

- **Widgets are ~80% of the way to plugins already**: one folder per widget (`app/Widgets/{Name}/` — definition class, Blade template, script, SCSS), a formal contract (`WidgetDefinition`), a registry that syncs declarative schema into the DB (`widgets:sync`, deploy-integrated since 341), per-widget assets built into a central manifest (`build:public`), and per-install activation (`widget_types.is_active`). What they lack to be *RimWorld* plugins: they live in the core repo, share the core's composer/npm dependency pool, can't carry migrations, and have no independent version.
- **Other seams, in descending plugin-readiness**: importers (registry pattern), email templates (handle-based), Filament resources (conventional but discoverable), public routes (centralized), the scheduler.
- **The entanglements** that resist extraction: shared Eloquent models (Contact is touched by everything), the migration/squash discipline, the single Vite build, the theme/token system, cross-feature Filament navigation, the test suite's monolithic fixtures.
- **The build spine it must dock into**: GHCR image built by `deploy.yml` from one repo, immutable VERSION tags, FM polling `/api/health` with that VERSION — a central build already exists; the question is whether it can *compose* from multiple repos.

### Phase 2 — Candidate end-states (present as a ladder, not a menu)

- **Stage A — module boundaries in-repo.** Formalize the plugin contract without leaving the repo: each candidate plugin becomes a self-contained directory (its models, migrations, resources, widgets, tests) behind an explicit interface + its own service provider; core stops reaching in. No repo split, no build change. *Value: proves the boundaries are real; this is where entanglements surface cheaply.*
- **Stage B — real packages, one workspace.** Candidate plugins become composer path-repositories + npm workspaces inside a monorepo; each has its own `composer.json`, version, migration set, and test suite; the central build assembles them. *Value: the packaging mechanics get proven while iteration stays cheap.*
- **Stage C — separate repos, central build.** The owner's stated vision: plugin repos + a slim core repo + a build repo/workflow that resolves a **plugin manifest** (which plugins, which versions) into the deployable image. Per-install composition = per-install manifest. *This is where the FM/deploy/VERSION story, cross-repo CI, and release discipline get real.*
- The ladder is also the **de-risking order** — each stage is independently valuable and independently stoppable, which matters for a few-weeks budget. Ask the owner where "the idea has been implemented, truly" lands on it — A proves the architecture, C proves the distribution story.

### Phase 3 — The hard-problem list (cost each honestly)

Walk these one at a time; for each, the doc records *the problem, the candidate answer, the cost class (hours / session / multi-session), and whether the pilot must prove it*:

1. Shared-model ownership (who owns `Contact`? — core-owns-models vs. plugin-owns-domain vs. events/extension-points).
2. Migrations per plugin (Laravel supports `loadMigrationsFrom`; interaction with the squash discipline + `migrate:fresh --seed` identity checks).
3. Front-end federation (per-plugin Vite builds vs. central build over workspace globs; the widget manifest already centralizes — extend or replace?).
4. Filament integration (panels/resources registered from packages — supported, but navigation/permissions/theming coherence needs a contract).
5. The plugin API surface itself (what core guarantees; how it's versioned; what a breaking change costs when plugins live in other repos).
6. Testing (per-plugin suites vs. the 3,100-test monolith; what runs in the central build's CI).
7. Per-install composition (manifest → build vs. runtime enable; where FM's node model and `widget_types.is_active` fit).
8. Load order / inter-plugin dependency (composer solves acyclic deps; RimWorld-style *patching* is the expensive property — likely explicitly deferred, get the owner's sign-off on that).
9. Repo/CI mechanics at stage C (auth between repos, version pinning, the immutable-VERSION contract, release cadence for a solo maintainer).

### Phase 4 — Verdict, plan, pilot

- **Feasibility verdict** in plain language: which stage is reachable in the available weeks, what it proves, what is deliberately left on the table.
- **Staged session arc** (the new roadmap spine): concrete next sessions with scopes — e.g., "377: extract {pilot} to a Stage-A module," "378: Stage-B packaging + central build," etc. The arc replaces the suspended launch schedule in the planning docs.
- **Pilot selection**: the best first extraction is probably a **leaf widget with its own assets and no shared-model writes** (LogoGarden / BarChart class) — end-to-end through whatever stage is chosen, as the template every later extraction follows. Confirm the candidate with the owner.
- **Go/no-go is a legitimate outcome in either direction** — "Stage A only, and that's the right size for this codebase's remaining life" is a valid, honest verdict if that's where the discussion lands.
