## The survey (ground truth, captured at 382 close)

**Plugin state:** `plugins/Events/` holds 56 files — provider, controllers + `routes/web.php`, quantities service, two observers, three mailables, reminders command, policy, `EventResource` + four pages + relation manager, both import wizard pages, the importer trio + field mapper, seven widgets under `Widgets/`, Filament/blade views. No `composer.json` yet. Activation is the `config/plugins.php` line (third entry).

**Schema state:** zero live migrations (the 382 squash); `database/schema/pgsql-schema.sql` carries all tables including `events`, `event_registrations`, `ticket_tiers` (the § 6.7 list), and a migrations table of 114 core rows. Models `Event`, `EventRegistration`, `TicketTier` and factories `EventFactory`, `EventRegistrationFactory`, `TicketTierFactory` are core. Core columns/relations referencing events tables that STAY core: `pages.type = 'event'` + `events.landing_page_id`, contacts/organizations event relations, `transactions` polymorphic `EventRegistration` subjects, import bookkeeping columns (§ 6.7).

**Test state:** ~29 events-titled Feature files (EventTest, EventCancellationTest, the three Session381 twins/mirrors, MultiQuantityRegistrationTest, RegistrationConfirmationTest, TicketTier tests, widget/contract-retrofit tests, importer tests, …); 58 files in `tests/` touch an event factory — the difference is cross-cutting core tests (transactions, pages, exports) that use events as fixture data and stay core. `phpunit.xml` declares two testsuites (Unit, Feature). `EventsRemovedTestCase` strips the config line after config load; its mirror tests assert both vanish (405/404, no admin, no schedule) and data-kept semantics (rows stay pending — they need the tables to exist).

**Packaging precedent (P6, session 382):** package `composer.json` with explicit `version: 0.1.0` (deterministic resolution without git — the image build excludes `.git/`), bound `^0.1` root require (unbound `*` fails `composer validate --strict`), root `path` repository entry, relative vendor symlink, Dockerfile plugin-manifest `COPY` before both composer-install layers. Standing guard `PluginPackageGuardTest` already globs `plugins/*/composer.json` — the Events manifest is covered by it the moment it exists (no auto-discovery, lockfile-pinned as a path package).

**Docker caveat (from the 382 log's P7 input):** Docker `COPY` with a glob (`plugins/*/composer.json`) flattens directory structure — the manifest copies must stay per-plugin lines (one more line per packaged plugin) or use a dedicated manifest-collection stage.

## Front-loaded decisions (settled at 382 prompt-draft time — reviewed with this prompt; do not reopen in session)

1. **Package: `nonprofitcrm/events`, on the P6 mechanics exactly.** Own `composer.json` — `"type": "library"`, explicit `"version": "0.1.0"`, PSR-4 `"Plugins\\Events\\": ""`, PHP constraint only. Root gains the second `path` repository entry + `"nonprofitcrm/events": "^0.1"`. No `extra.laravel.providers` (guard-enforced); `config/plugins.php` stays the sole activation + ordering authority. No composer-level dependency on core or on Payments — the Payments soft dependency stays capability-detection only (surface 13; a composer `suggest` waits until Payments is itself a package). Dockerfile: one added per-plugin manifest `COPY` line in each stage (no glob — the flattening caveat). Payments stays a plain in-repo folder.
2. **Models and factories stay core at P7.** The plugin takes the *schema*; core keeps `Event`/`EventRegistration`/`TicketTier` and their factories. Rationale: the engine seams that read these models — resolver arms, page-builder sources, content import/export, `RandomDataGenerator`, `EventLandingPageFactory`, the `transactions` polymorphic subjects — are core code programming against core models, and `EventModuleBoundaryTest` (zero allowlist) bans core→plugin reaches; moving the models means contract-mediated model access across all those seams, a lift that is not P7's slot. Consequence stated honestly: "vertical fully self-contained" remains incomplete until a later arc position takes the model move deliberately (candidate: alongside Stage C extraction, when the seams get their contract treatment). *(This is the one genuinely reviewable call in this prompt — everything else is mechanics.)*
3. **Schema ownership redraw, per § 6 disposition 7:** the plugin gains `database/migrations/` with create-table migrations for the three events tables, authored from the current dump DDL byte-faithfully (FKs to core tables included; creation order `events` → `ticket_tiers` → `event_registrations` per FK direction). `EventsServiceProvider` registers them via `loadMigrationsFrom`. Core's dump is regenerated WITHOUT the three tables (procedure: `migrate:fresh` from the current full dump on local, drop the three tables, `schema:dump`; the migrations table keeps its 114 core rows — plugin migration rows are added at install time on each composition, which is the deterministic order made real: **core dump → enabled plugins' migrations → seeders**).
4. **Vanish-test semantics (the carried design note, resolved): disabled ≠ uninstalled.** The strip-the-line fixtures (`EventsRemovedTestCase` + mirrors) model *installed-then-disabled*: schema present, activation stripped, data kept. The fixture therefore keeps the plugin's migrations applied to the test database (mechanism: the fixture loads the plugin's migration path explicitly even though the provider never boots — implementation detail, session's call) so every existing data-kept assertion passes unchanged. *Never-installed* is a different composition, proven by the per-composition identity check (decision 5), not by per-test fixtures. Document both semantics in the contract doc's surface 5.
5. **Per-composition fresh-install identity check (verified runs, not standing tests):** (a) full composition — core dump + Events migrations + seeders reproduces today's exact schema (diff `schema:dump` output against the pre-redraw dump; the only permitted delta is migrations-table rows for the plugin's migrations) plus the 348/382-style seeded-data spot verification; (b) events-absent composition — core dump + seeders boots clean, public + admin smoke pass, no events tables present. Composition (b) is the first fresh-install-without-a-vertical proof in the repo's history — record its procedure in the log for P8's activation-layer work.
6. **Test-suite move: the events-slice Feature files move to `plugins/Events/tests/`,** registered as a third `phpunit.xml` testsuite (name `Events`) so `php artisan test`, paratest, `--exclude-group=slow`, and CI all keep running them unchanged; `autoload-dev` gains the plugin test namespace if files carry classes (Pest closures usually don't). Membership rule: a file moves if its *subject* is plugin-owned behavior (controllers, observers, mailables, widgets, importer, admin pages, the 381 twins/mirrors); a file stays core if events are merely its fixture data (transactions, pages, exports, landing-page factory — the 58-minus-29 set). The reduction pass rides along: de-duplicate and trim while moving, deletions logged. The `RemovedTestCase` fixtures stay core (`tests/Fixtures/Plugins/` — they are core's proof about core's loader). Fast/slow group discipline unchanged; expect the fast-suite count to move, not shrink dramatically.
7. **Contract doc at close:** surface 5 (Migrations) → **PROVEN** with the disabled-vs-never-installed semantics recorded; surface 6 notes seeder posture unchanged (base seed writes no events rows; the demo/fixture layer stays core until the configuration-pack layer exists); package-shape section gains the second consumer + the per-plugin manifest-COPY rule; bump 0.6.0 → 0.7.0, changelog.
