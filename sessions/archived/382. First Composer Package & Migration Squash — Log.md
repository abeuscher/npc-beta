## P7 input (package-mechanics learnings + carried design notes)

**What the mechanics revealed, for the vertical-as-package session:**

1. **Explicit `version` field is mandatory** in each package manifest — resolution must not depend on git branch guessing (absent in image builds; churns the lock across branches).
2. **Bound constraints, not `*`** — `composer validate --strict` is the gate and rejects unbound requires; pair `"version": "0.1.0"` with `"^0.1"`.
3. **Docker `COPY` globs flatten** — `COPY plugins/*/composer.json plugins/` would put every manifest in one directory. Manifest copies stay per-plugin lines (one added line per stage per package), or a dedicated manifest-collection stage if the line count ever matters.
4. **The in-image proof procedure** (cheap, reusable): `docker build --target app`, then `docker run --rm --entrypoint sh <image> -c 'ls vendor/<vendor>/ && php -r "require \"vendor/autoload.php\"; var_dump(class_exists(...));"'` (bypass the entrypoint — its volume chown makes plain `docker run` hang).
5. **`PluginPackageGuardTest` covers new manifests automatically** — no per-package guard work at P7.

**Carried design notes (folded into the 383 prompt's decisions):**

- **EventsListing → BlogPager cross-plugin build input:** a plugin widget declaring a core widget's stylesheet as a build input is fine while everything shares one repo (asset paths are repo-relative build inputs, not namespace reaches); it becomes a real coupling question at P9 (separate repos). No P7 action; recorded in the 383 survey.
- **Vanish-test semantics once schema is plugin-owned:** resolved in the 383 prompt's decision 4 as *disabled ≠ uninstalled* — strip-the-line fixtures keep the plugin's schema on the test DB (data-kept semantics unchanged); *never-installed* is a composition proven by the per-composition fresh-install identity check, not by per-test fixtures.
