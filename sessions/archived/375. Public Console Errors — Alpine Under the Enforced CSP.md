## The diagnosis — verified against production at 374, do not re-derive

A headless-browser audit (`bin/console-audit.mjs`, committed at 374) was run against **https://nphelper.com** on 2026-08-17. Findings:

- **Every sampled page** (`/`, `/about`, `/contact`, `/demo`, `/docs`, `/pricing`, `/privacy-policy`, `/terms-of-use`) emits **exactly 4 console entries**: 2× `Alpine Expression Error` warnings + 2× uncaught `EvalError`.
- All four trace to one cause: the enforced public CSP — `script-src 'self' 'nonce-…'` with **no `'unsafe-eval'`** — blocks Alpine's expression evaluator (`new Function()`). The erroring expressions on the marketing pages are the **Nav widget's** dropdown component (`app/Widgets/Nav/template.blade.php:182` — inline `x-data="{ activeDropdown … }"`, `@keydown.escape.window="closeAll()"`, etc.).
- **Consequence is functional, not cosmetic:** the uncaught `EvalError`s mean Alpine components never initialize on production — desktop nav dropdowns, `customSelect`, the `theme` store, and every other Alpine-driven public behavior are dead, and have been since the S1 CSP deploy (session 370). Nobody noticed because the S1 verification didn't include a console/behavior pass on the built public bundle.
- **Nothing else is wrong:** all homepage assets return 200 (both Vite bundles, the widget bundle, all `storage/cas` media); no failed requests, no 4xx/5xx, no other JS errors on the sampled pages. This is one defect class, sitewide.
- The same CSP is enforced locally (the middleware does not gate on environment for the public surface), so **the errors reproduce on the local stack** — the full fix loop runs locally, with production as final confirmation.
- The admin panel is unaffected: `SecurityHeaders.php` grants `'unsafe-eval'` to admin paths only (Filament requires it) — that carve-out stays.

**Alpine inventory floor** (from a first-pass grep at 374 — the session's audit must complete it): `resources/js/public.js` (imports Alpine, registers `customSelect`, defines the `theme` store, calls `Alpine.start()`), plus inline `x-data` in the templates of at least: **Nav, LogoGarden, BarChart, SocialSharing, BlogListing, SetupChecklist, EventMiniCalendar, PortalSignup, DonationForm, RandomDataGenerator, EventsListing**. Check `resources/js/portal/` and any public Blade layouts/partials too.

## What this session ships

1. **The complete audit** — every Alpine usage on the public + portal surface, classified: trivial toggle (candidate for CSS or 5-line vanilla JS) vs. stateful component (candidate for a registered CSP-build component) vs. dead code (remove).

2. **The migration.** Recommended architecture, to confirm at the Open Gate after a one-widget spike:
   - Swap the public bundle to **`@alpinejs/csp`** (the vendor's CSP-compatible build — same reactivity, but expressions are limited to registered-component property/method references; no inline evaluation, which is exactly the property the CSP wants).
   - Every inline `x-data="{ … }"` object becomes a **named component registered in the bundle** (`Alpine.data('navDropdown', …)` etc.), with per-instance config passed via `data-*` attributes read in `init()` rather than expression arguments.
   - Every inline statement (`@click="open = !open"`, `@keydown.escape="closeAll()"`) becomes a **method reference** on the registered component.
   - Widgets whose Alpine usage is a trivial show/hide may drop Alpine for CSS (`:hover`/`:focus-within`/checkbox pattern — the mobile nav from 334 is the house example) or a few lines of vanilla JS in the widget's bundled `script.js` — per-widget call, made at the gate, not ad hoc.
   - If the spike shows `@alpinejs/csp` can't cleanly express what the widgets need, the fallback is a **fully vanilla** public surface (Alpine removed from `public.js` entirely) — more code, zero framework caveats. Owner is explicitly open to either; bring the recommendation.

3. **Zero-error proof, twice.** Local: `bin/console-audit.mjs` against a page set that exercises **every migrated widget** (marketing pages + a blog post + an event landing page with the registration widget + the donation page + portal sign-in + a scratch page hosting the long-tail widgets — build it locally if no existing page places them). Production: after the owner merges and deploys (**VERSION bumped to `0.375.<N>` first** — the deploy enforces immutable tags), re-run with `BASE=https://nphelper.com` and report the zero.

4. **Standing guards** (confirm at gate):
   - A **Playwright spec**: key public pages emit zero console errors/pageerrors against the local stack — the permanent regression net for this class. (This earns its place; it would have caught the S1 regression on the day it happened.)
   - A **convention-drift Pest test** banning inline Alpine expression shapes (`x-data="{`, statement-bearing `@click="` etc.) in `app/Widgets/**/template.blade.php` + public views — mirrors the existing convention-drift guard idiom (session 345), so the constraint survives future widget authors.

5. **Docs**: a short note in the security track doc (`sessions/tracks/security-hardening.md`) recording that S1's public CSP is now *proven compatible* with the shipped front-end (the residual "admin CSP Report-Only" note stands unchanged); update `docs/app-reference.md` only if the bundle entry points change names.

## Runbook notes (environment specifics)

- Node: `PATH="/home/al/.nvm/versions/node/v24.14.1/bin:$PATH"` — bare `npm`/`node` resolve to the Windows binaries and fail.
- `bin/console-audit.mjs` must run **from the repo root** (it resolves the repo's installed Playwright). It is a standalone script, not a test-runner spec — it touches no database and is safe against production.
- Builds: template + bundle changes ⇒ `npm run build`; widget `script.js` / `WidgetType.assets` changes ⇒ **also** `php artisan build:public` (stale widget manifests silently break downstream — when in doubt, run it).
- Pest and Playwright never run in parallel (they collide on DB/FPM and take the local site down; `docker compose restart nginx` recovers stale upstreams).
