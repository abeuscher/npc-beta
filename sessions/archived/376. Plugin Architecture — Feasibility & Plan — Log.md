### Phase 1 — Code inventory

- Three parallel read-only inventories grounded the discussion: the widget system end to end, the other extension seams, and the build/deploy spine.
- Headlines: widgets are the most plugin-shaped code (41 folders, formal `WidgetDefinition` contract, registry + deploy-integrated `widgets:sync`, out-of-band central asset build server) but fall short of plugins on three counts — hardcoded 41-class registration in `WidgetServiceProvider`, DB-mediated asset paths, and model-reaching templates (Nav, DonationForm, the portal set). The clean leaf widgets (LogoGarden, BarChart, TextBlock) are pure render functions over the data-contract path. Elsewhere: consistent registry/handle patterns but zero runtime pluggability; the panel provider's inline route closure and the squashed schema are the biggest structural obstacles; the PHP side is one monolithic composer package (no path repos, no workspaces), while the deploy pipeline (immutable VERSION → GHCR → FM `/api/health`) is a working central build to dock into.
- **Drift noted:** the session prompt asserted per-install widget activation via `widget_types.is_active`; no such column or mechanism exists anywhere. Per-install composition is *less* built than the prompt assumed — recorded in the plan doc's property table.
- **Drift noted (planning):** the session charter's orphaned-entry list omitted F1 (on-demand donation-payment E2E); dispositioned parked with its launch-rehearsal peers.

### Phase 2 — Discussion: motivations, principles, the core line

- Motivations settled: the architecture itself; the LLM context-window benefit (with the load-bearing correction: savings come from boundaries + contracts, not the repo split — the FM contract relationship is the in-house proof); the business premise (vertical SaaS: a niche = a manifest/config pack, not new engineering). Retrofit chosen over greenfield (portfolio claim, no concrete greenfield product, scope-creep risk).
- Principles fixed in the plan doc: the contract is the load-bearing artifact; thin core = small shared surface, modularity = small working set; litmus test (plugin only if some install would exclude/replace it); sockets vs. parts; plugins never patch plugins.
- Core/plugin map agreed: core = identity (minimal `Contact`), admin shell + sockets, page/widget engine, plumbing, fleet/deploy spine; plugins = domain verticals (DLC analog), foundation plugins (Payments), widgets, integrations; importers ride their domain plugin.
- Question dispositions (owner rulings): contact extension via **relations on id only** (also the HIPAA-open-door direction); **Payments = foundation plugin**, verticals never depend on verticals, soft deps via capability detection (Events works payment-less — the $0/comp path proves it); **tests per-plugin**, monolith dismantled with reduction at extraction time; three Filament conventions approved (core-owned nav groups + sort weight; permissions seeded-at-enable, super-admin-only default; core-owned admin theme); composition = superset niche images + per-install activation (three-tier changeability model; disabled = inert, data kept). Niche selection deferred to owner research.
- Owner content directive applied: game-inspiration references minimized throughout the doc set (one acknowledgment retained, framed as divergent-by-design).
