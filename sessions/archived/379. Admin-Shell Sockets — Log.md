## What was built

### Phase 1 — Route-closure decomposition

- `AdminPanelProvider`'s ~100-line inline `->routes()` closure decomposed into eleven per-feature files under the new `routes/admin/`: `two-factor.php`, `invitations.php`, `media.php`, `quickbooks.php`, `theme.php`, `dev-tools.php`, `setup-checklist.php`, `exports.php`, plus the three existing builder API files moved in via `git mv` and renamed (`admin-api.php` → `builder-page.php`, `admin-dashboard-api.php` → `builder-dashboard.php`, `admin-record-detail-view-api.php` → `builder-record-detail.php`). The only external reference to the old basenames — one line in `docs/runbooks/permission-matrix.md` — updated.
- The closure shrank to an ordered pull list (`$pulls` map → `Route::group($attributes, base_path(...))`); the three builder pulls keep their `prefix` + `Authenticate` at the pull site (the pre-decomposition shape); pull order preserves the original inline registration order. Load-bearing comments (2FA redirect-loop avoidance, demo-upload gate, export gating) traveled with their routes.
- **Route parity: exact.** `route:list --json` captured before any change and diffed after — 274 routes, byte-identical JSON (names, URIs, methods, middleware, order). Re-verified after Phase 2's socket wiring: still identical. Empty diff both times.
- Drift check at open: none — the session prompt's survey (538-line provider, ten clusters) matched the code exactly.

### Phase 2 — The plugin admin socket

- New core namespace `app/Plugins/`: `AdminContribution` (value object: plugin name, resources/pages discovery path+namespace pairs, in-panel route file, permission names) and `PluginAdminRegistry` (singleton; `register()`, `all()`, `permissions()`).
- `PluginServiceProvider` binds the registry before the plugin loop, so plugin providers declare contributions from their own `register()`.
- `AdminPanelProvider` consumes the registry: discovery paths join core's `discoverResources`/`discoverPages`; plugin route files are pulled into the `->routes()` group **always wrapped in Filament's `Authenticate`** — a plugin admin route can never opt out of panel auth (session call, security-first).
- `PermissionSeeder` gained an idempotent registry sweep: plugin-declared permissions `firstOrCreate`d (guard `web`), granted to no shipped role — super-admin reaches via the `Gate::before` bypass (the `manage_account` precedent). Disabling a plugin stops seeding but never deletes.
- **SocketProbe fixture plugin** at `tests/Fixtures/Plugins/SocketProbe/` — one Filament page (`Tools` group, sort 97, gated on its own `use_socket_probe` permission), one route file, one permission. Enabled via `SocketProbeTestCase`, which appends the provider to `config('plugins')` between config-load and provider registration (`afterBootstrapping(LoadConfiguration::class)`) — the exact moment a real `config/plugins.php` entry takes effect. Never listed in the shipped config.
- Tests: `PluginAdminSocketSession379Test` (6 — registration, page discovery + nav group/sort, route behind `Authenticate` + panel middleware, guest-redirect/super-admin-200, idempotent no-role permission seeding, permission-gated page access) and `PluginAdminSocketRemovalSession379Test` (3 — the remove-the-line mirror: no contribution, no page/routes, no seeded permission on the plain application).
- Session calls logged: registry as dedicated classes in `app/Plugins/` (not statics on the provider); permission sweep in `PermissionSeeder` (not a `plugins:sync` command); no help-doc stub for the fixture page (test-only, vanishes with the config line — the stub rule applies to shipped pages).

### Phase 3 — The guard and the contract doc

- Standing guard `PluginAdminCssGuardTest`: bans `.css` files anywhere under `plugins/`, and `viteTheme(`/`renderHook(`/stylesheet-link/admin-css tokens in plugin PHP — zero allowlist. LogoGarden's widget SCSS (public bundle) passes clean; a scan-set coverage pin mirrors the `WidgetTemplateBoundaryTest` pattern.
- `docs/plugin-contract.md` → **v0.3.0**: surfaces 3 and 4 rewritten with the concrete mechanics (registry shape, `routes/admin/` layout, the three conventions, the Authenticate wrap, the vanish guarantee), fixture tests named, **status kept DECLARED** per the honesty rule — promotion to PROVEN waits for the first shipping plugin with admin pages (P5+).

## Security considerations

The admin route surface was proven byte-identical before and after the decomposition (empty `route:list --json` diff, including middleware), so no access posture changed on any existing route. New socket mechanics are fail-closed: plugin in-panel routes are force-wrapped in `Authenticate` by core with no opt-out; plugin permissions seed granted to no shipped role (super-admin only via the existing gate bypass); the fixture page demonstrates permission-gating (developer-role user gets 403). The plugin-admin-CSS guard prevents a plugin from restyling (and thus spoofing) admin chrome. Nothing changed on who can access existing admin pages.
