## The survey (ground truth, captured at 383 close)

**Activation today:** `config/plugins.php` returns a flat ordered list of three provider class strings (LogoGarden, Payments, Events). `App\Providers\PluginServiceProvider::register()` binds the three registries, then registers each listed provider in order. No filter, no per-install state, no handle concept. The list doubles as "installed" and "enabled" — indistinguishable today.

**The proven disabled semantics:** `EventsRemovedTestCase` / `PaymentsRemovedTestCase` strip one provider from `config('plugins')` after config load, before providers register. Their mirror tests (`EventsPluginRemovalSession381Test`, `PaymentsPluginRemovalSession380Test`) assert the full vanish surface: provider not loaded, routes gone (405/404 fall-through), admin pages gone, schedule empty, observers detached, importer withdrawn, widget rows dropped on next `widgets:sync`, **data kept and queryable**, other plugins untouched. Since 383, `EventsRemovedTestCase` also registers the plugin's migration path directly on the migrator (disabled ≠ uninstalled — schema present without the provider booting).

**Schema × activation (from 383):** plugin migrations register in the provider's `boot()` via `loadMigrationsFrom`. A plugin that never registers contributes no migrations — on a fresh install its tables never exist; on an existing install they persist untouched. Enabling later runs its pending migrations on the next `migrate` (deterministic order: core dump → enabled plugins' migrations → seeders). Runtime-disabled installs keep their schema, so the composition-debt class from the 383 P8 input (admin tools querying plugin-owned tables) does **not** bite them — it bites only never-installed compositions.

**Ops surface:** per `docs/app-reference.md`, `.env` on a droplet is read at container start (`env_file:`), so a flag change is: edit `.env` → `docker compose up -d` (recreate) → `config:clear` — an existing, documented procedure. § 4d names FM's config-push channel as the eventual delivery mechanism for exactly this file; the FM side is future work, not this session.

**Image state:** one superset image already builds and ships (P6/P7 — both packages resolve in-image; the 382-log in-image proof procedure is reusable). The e2e stack and both droplets set no flag and keep running the full composition.

**Naming precedent:** plugin folders are `plugins/{PascalName}`; packages are `nonprofitcrm/{kebab-case}` (`logo-garden`, `events`); the admin socket uses a lowercase handle (`'events'`). Kebab-case of the PascalName is derivable from every provider FQCN (`Plugins\{PascalName}\…`) with no new registry.

## Front-loaded decisions (settled at 383 prompt-draft time — reviewed with this prompt; do not reopen in session)

1. **The activation store is per-install configuration, read at bootstrap: `PLUGINS_DISABLED`, a comma-separated list of plugin handles** (e.g. `PLUGINS_DISABLED=events` or `events,logo-garden`), surfaced through a new small config file (e.g. `config/plugin-activation.php` → `['disabled' => …]`) so it is config-cache-safe. Rationale: provider registration happens at bootstrap, before the database is guaranteed to exist (fresh containers, `migrate` itself, workers, tests) — env-backed config is the only store that is always readable there; it is flip-without-rebuild (tier 1: edit `.env`, recreate container — the documented procedure); and it is precisely the file FM's config-push channel already delivers per install. A DB-backed store with an admin toggle is deliberately NOT built (bootstrap chicken-and-egg, a new security surface, and the business flow runs through FM's channel anyway — record as the backlog line for whenever the FM control panel wants it). `config/plugins.php` is untouched.
2. **A *disabled*-list, not an *enabled*-list, and the mechanism is subtraction at the loader.** Default (unset/empty flag) = everything installed runs — today's behavior, zero migration risk for every existing install, and the superset-image posture (§ 4d: include everything, let activation decide). `PluginServiceProvider::register()` filters the `config('plugins')` list by the disabled set before registering — the exact seam the RemovedTestCase fixtures already prove, which makes runtime-disabled ≡ strip-the-line **by construction** (same list, same subtraction, earlier actor). Ordering is untouched (subtraction never reorders). `.env.example` gains `PLUGINS_DISABLED=""` with a comment (concrete-values rule: the explicit empty default, not an absent key).
3. **Handles are derived, not declared: kebab-case of the plugin's PascalName folder/namespace segment** (`LogoGarden` → `logo-garden`, `Payments` → `payments`, `Events` → `events`), computed from the provider FQCN in the loader. No new registry, deterministic, matches the composer package names. The handle set is closed over `config/plugins.php` — which enables decision 4.
4. **Unknown handles fail the bootstrap.** A handle in `PLUGINS_DISABLED` that matches no installed plugin throws at registration time with a message naming the bad handle and the valid set. A typo silently ignored would leave a plugin running that the operator meant to disable (security-over-usability); failing at bootstrap is caught immediately by the image healthcheck / `compose up --wait` and the deploy pipeline. Disabling an installed-but-already-disabled handle twice is idempotent by construction (set semantics).
5. **Test shape: the mirrors are the spec; the new tests prove equivalence and the seams the fixtures can't.** (a) A new fixture (`EventsDisabledViaFlagTestCase`-style) boots with `config('plugin-activation.disabled') = ['events']` set the same after-config-load way, and a test file asserts the load-bearing vanish points (provider not loaded, routes gone, schedule empty, widgets dropped on sync, data kept) — assertion content mirroring the 381 file, trimmed to the points that prove the *filter*, since full vanish depth is already pinned by the existing mirror. (b) A generalization test disables `logo-garden` and `payments` by flag and asserts their providers don't load while Events still does — LogoGarden's first vanish coverage, riding free. (c) Unit-level tests for the handle derivation and the unknown-handle throw. (d) The existing RemovedTestCase fixtures and mirrors are untouched. No standing test boots a real container — the superset-image run is a verified run (decision 6).
6. **The workspace-assembly proof is the superset-image run (verified run, recorded in the log):** build the image once locally (382 in-image procedure), then boot the same image twice against a scratch database — (a) no flag: full composition (routes registered, `widgets:sync` → 41 rows, migrations 117); (b) `PLUGINS_DISABLED=events`: events surface vanished at runtime (register POST 405, JSON 404, no events widget rows, schedule empty, migrations 114 on a fresh DB — the flag-made version of 383's composition (b)), then flip the flag off, restart, `migrate` → the plugin's three migrations apply and the surface returns — **the enable-later runbook proven end to end**. Record the exact commands as the tier-1 runbook (the future FM-channel payload is these steps). This — one image, compositions chosen per install at runtime — is the honest Stage B reading of "the central build assembles the workspace"; generalizing the build over a distribution manifest and external repos is P10, not this session (see Open questions).
7. **Contract doc at close:** surface 1 rewritten for the two-layer model — *installed* (in the image; `config/plugins.php`, the ordering authority) vs *enabled* (installed minus the per-install disabled set); filter-at-loader mechanics; derived handles; strict unknown-handle posture; the tier-1 flip runbook including restart + `migrate`-on-enable; the explicit note that runtime-disabled reproduces the strip-the-line semantics the mirrors assert. Surface 5 gains the enable-later cross-reference. Bump 0.7.0 → 0.8.0, changelog entry. Not boundary-touching (no FM surface; the health-payload plugin manifest stays the § 4d future item).
