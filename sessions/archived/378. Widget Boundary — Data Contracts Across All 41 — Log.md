## What was built

### Phase 1 — The seam: multi-contract plumbing

- `WidgetDefinition::dataContracts(array $config): array` — named contracts (`['event' => …, 'member' => …]`); default wraps the singular `dataContract()` under `'default'`, so the existing single-contract widgets are untouched and keep the unkeyed `$widgetData` shape.
- `WidgetRenderer` resolves the named list through the existing `ContractResolver::resolve()`; single contract delivers unkeyed, multiple deliver keyed by name; `mergeUserQueryConfig` applies to the primary (first) contract only. The page-context skip optimization now also requires `fields === []`, so field-declaring page-context contracts (brand reads) always resolve.
- `mergeUserQueryConfig` now carries `cardinality` and `requiredPermission` through the contract rebuild — a latent drop (no widget combines a query panel with either field today), closed before the new arms could inherit it.
- `site_name` added to `PageContextTokens::TOKENS` as a site-global token (`SiteSetting::get('site_name', config('app.name'))`); resolvable with no current page via a new `globalValues()`, which the page-context projector falls back to.

### Phase 2 — Retrofit by category

- **New resolver arms** (all fail-closed per-field via `SystemModelProjector` / an equivalent service filter): `fund` (list; active/non-archived, name order), `membership_tier` (list; active/non-archived, sort order), `navigation_menu` (single by id — **UUID string, not int**; visible three-level item tree with hrefs/targets/link flags; dropdown gradient precomputed into `drop_fill_gradient_css` from contract filters, retiring the template's `GradientComposer` call), `portal_member` (single; resolves `auth('portal')` inside the arm, logged-out ⇒ `['item' => null]`; `event_registrations` nested DTO loads only when declared), and a new `SOURCE_SERVICE` source (`setup_checklist`, `scrub_counts`) whose arms hard-gate on super-admin.
- **Twelve templates rewritten to pure `$widgetData` renderers:** DonationForm, Nav, PortalSignup (multi-contract: tiers + brand), PortalLogin, PortalForgotPassword, PortalAccountDashboard, PortalChangePassword, PortalContactEdit, PortalEventRegistrations, EventRegistration (multi-contract: event + member presence), SetupChecklist, RandomDataGenerator (its `StripeMode::isLive()` support-class read stays — not a banned reach).

Promoted to the core Blade component `<x-widget-buttons>` (`resources/views/components/`), per the same settled rule that put core components outside the scan; the four including templates (ButtonRow, Hero, PricingChart, TextBlock) now use the component.

## Security considerations

The portal-member arm is the PII-sensitive surface: it projects only contract-declared fields (non-leak test asserts undeclared member/contact fields never appear in the DTO or rendered HTML path), resolves the portal guard inside the arm, and loads the registrations relation only when declared. The two super-admin tool arms hard-gate inside the resolver, so a template can no longer accidentally drop the gate. The permission-gate field drop in `mergeUserQueryConfig` was latent (no affected widget) and is closed. The standing guard makes the whole class of template-side data reaches un-reintroducible.
