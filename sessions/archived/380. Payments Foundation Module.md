## The survey (ground truth, captured at 379 close)

The payment rails are small and shallow — **every path is redirect-to-Stripe-hosted-Checkout**; no Stripe.js, no Elements, no client-side tokenization anywhere. The SDK (`stripe/stripe-php` v16) arrives transitively via `laravel/cashier` v15, and **Cashier itself is entirely unused** (no `Billable`, no cashier config, no subscription tables; ADR `docs/decisions/005-stripe-as-financial-source-of-truth.md` claims otherwise and is stale on that point).

**The core to carve (~1,100 lines, only two direct-SDK sites):**

- `app/Services/StripeCheckoutService.php` (167) — the only Checkout Session factory; news up `StripeClient` inline; `defaultImageUrl()` reads per-flow SiteSettings.
- `app/Http/Controllers/StripeWebhookController.php` (506) — the whole inbound surface: signature verify, event router, five handlers (`checkout.session.completed` fan-out keyed on metadata: `donation_id` / `event_registration_checkout` / `membership_id` / `product_price_id` / generic fallback; plus `invoice.payment_succeeded`, `invoice.payment_failed`, `payment_intent.payment_failed`, `refund.created`). Writes vertical models directly (Donation, EventRegistration, Membership, Purchase, Transaction, Contact) and queues two Mailables. Idempotent by `stripe_id` / session-id / pending-status checks; handler exceptions swallowed into a 200.
- `app/Observers/ProductPriceObserver.php` (58) — the second direct-SDK site (Stripe Price archive-and-create on save). **No real test coverage** (the inbox `[test-integrity]` item; deleted tests passed with the observer unregistered).
- `app/Support/StripeMode.php` (25) — `isLive()` sniffs the key prefix off the SiteSetting directly (divergent read path); used only by the Random Data Generator guard.

**The seams:**

- All four verticals (donations, event ticketing, products, memberships) reach Stripe through `app(StripeCheckoutService::class)->createSession(...)` — call sites in `DonationCheckoutController` (94), `ProductCheckoutController` (68), `MembershipCheckoutController` (174), `EventController` (169), `Portal/EventRegistrationController` (159, near-verbatim duplicate of EventController's paid branch). Shared pattern: create pending row → try Stripe → on throw delete row + form error → on success stash `stripe_session_id` + redirect; the webhook promotes pending later.
- The de-facto capability check is `empty(config('services.stripe.secret'))`, copy-pasted five times (the five controllers) plus a silent early-return in `ProductPriceObserver`. Config comes from `AppServiceProvider` (~L133-135) copying three SiteSetting rows into `config('services.stripe.*')` at boot — `config/services.php` has no stripe block at all.
- `app/Filament/Widgets/DashboardIntegrationStatusWidget.php:22` reads `config('services.stripe.key')` — a key nothing sets — so **Stripe never shows as connected on the dashboard** (live bug).
- `EventRegistrationQuantities` (166, vertical service) owns the paid-vs-free decision (`isPaid()`) and builds Stripe-shaped line items (`stripeLineItems()`) with no SDK import.
- Webhook route: `POST /webhooks/stripe` in `routes/web.php` (~L37), name `webhooks.stripe`, no auth; CSRF exemption via `bootstrap/app.php` (`/webhooks/*`).

**The free paths (must not change):** zero-total ticket orders branch on `EventRegistrationQuantities::isPaid()` in both event controllers (`source=human`, confirmation inline, Stripe never reached); no-tier events are always free; comp memberships are created directly in `Portal/SignupController` while `MembershipCheckoutController` rejects $0 tiers. `ticket_tiers.is_complimentary` is display-only.

**Receipts:** the annual tax receipt (`DonorsPage::sendReceipts`) is fully Stripe-free (reads donation state only). The per-gift acknowledgment Mailable has zero Stripe references — only the webhook's call site couples them. Both mail classes and the receipt models stay core.

**What must NOT move — client billing (CB):** `app/Services/Billing/*`, `EnforceSuspensionState`, `AccountPage`, `config/fleet.php`, and the suspension views hold no Stripe SDK or config references by design. `tests/Feature/Infrastructure/ConventionDriftTest.php` enforces the two-Stripes boundary (~L140-198): bans `stripe_billing`/`vendor_stripe` tokens app-wide, bans Stripe reaches from CB files, and carries a **positive control asserting `app/Services/StripeCheckoutService.php` matches** — that control must move with the file. Binding invariant: under `admin_locked` the public checkout deliberately stays up (only the back office locks); under `site_off` everything goes down. The carve must not change that asymmetry.

**Storage:** no Stripe customer table, no payment methods stored anywhere. Stripe IDs live in columns on `donations`, `event_registrations`, `memberships`, `purchases`, `product_prices`, `transactions` — all stay put (no schema changes at P4). `Transaction::recordStripe()` is the single write path for Stripe money and stays core. Dead artifacts noted for the backlog: `products.stripe_product_id` (zero references), `resources/views/events/show.blade.php` references a nonexistent `events.checkout` route (legacy pre-widget blade).

## Front-loaded decisions (settled at 379 prompt-draft time — do not reopen in session)

1. **Module shape:** `plugins/Payments/`, namespace `Plugins\Payments\`, provider `PaymentsServiceProvider` listed in `config/plugins.php` (surface-1 shape, LogoGarden precedent). Moves with namespace change: `StripeCheckoutService`, `StripeWebhookController`, `ProductPriceObserver`, `StripeMode`. Internal folder layout is the session's call (log it). The provider owns: observer registration, the webhook route registration, the SiteSetting→config injection (moves out of `AppServiceProvider` — when the plugin is absent, `services.stripe.*` is simply never populated), and the capability declaration.
2. **Capability API (surface 13) is core-owned, mirroring the 379 registry pattern.** `App\Plugins\CapabilityRegistry`, singleton bound in `PluginServiceProvider` alongside `PluginAdminRegistry`. Plugins declare `provide(string $name, Closure $enabled)` at register/boot time; consumers ask `present('payments')` (a registered plugin provides it) and `enabled('payments')` (present AND the resolver returns true). Payments' resolver is `filled(config('services.stripe.secret'))` — the same truthiness the five copy-pasted guards test today, so the swap is behavior-preserving by construction. The five controller guards and the observer's early-return route through `enabled('payments')`; error copy and response shapes unchanged. `StripeMode` keeps its live-key sniff (it answers a different question) but moves into the plugin.
3. **The checkout seam is a core-owned contract, not a plugin class import.** New interface `App\Payments\Contracts\CheckoutProvider` (mirrors the `app/Widgets/Contracts/` convention) declaring `createSession(...)` and `defaultImageUrl(...)` with the exact current signatures. The plugin binds its implementation; verticals resolve the interface, never `Plugins\Payments\*`. Guard rule from day one: `app/` never references the `Plugins\Payments\` namespace. `EventRegistrationQuantities::stripeLineItems()` stays put un-renamed — it builds the array format the contract accepts and holds no SDK reference; renaming is cosmetic and deferred.
4. **The inbound direction stays as-is; the inversion is P5's.** The webhook controller keeps writing core models directly — plugin→core hard dependency, allowed by the dependency rules. The typed-event inversion (surface 10: the module emits payment-settled events, verticals listen) lands with the first vertical extraction, scoped to that vertical's handlers, because that is when a webhook write would become a plugin→vertical reach. Recorded in the contract doc as the named P5 work, not silently deferred.
5. **Webhook route parity.** The plugin provider registers `POST /webhooks/stripe` with name, URI, and middleware identical to today; the `/webhooks/*` CSRF exemption stays core in `bootstrap/app.php` (it is path-policy, not plugin behavior). Route-list parity proven by a before/after `route:list --json` diff recorded in the work log (the 379 method).
6. **Dependency hygiene rides along:** `composer remove laravel/cashier` + `composer require stripe/stripe-php` (pin the currently-installed major). Survey basis: Cashier is entirely unused. If removal surfaces any hidden usage, abort the removal, keep both packages, log one line — do not chase it. ADR 005 gets a one-paragraph correction (Cashier claim; the module's new location), not a rewrite.
7. **Standing guard: `PaymentModuleBoundaryTest`.** Bans, outside `plugins/Payments/`: `Stripe\` namespace tokens and `StripeClient` anywhere in `app/` (zero allowlist), `Plugins\Payments\` references anywhere in `app/` (the seam rule from decision 3), and `config('services.stripe.` reads outside an enumerated, comment-justified list (expected survivors: `SetupChecklist`'s onboarding checks; enumerate what actually remains at session time and log it). In the same pass, update `ConventionDriftTest`'s positive control to the moved path. The CB-side bans are untouched.
8. **Riders (fix in session):** (a) `DashboardIntegrationStatusWidget` routes through `enabled('payments')` — fixing the never-shows-connected bug as the natural first consumer of the API; (b) the ProductPriceObserver test backfill (inbox item, absorbed) — a Stripe-boundary-mocked test proving archive-and-create fires on price save and stays inert when payments is unconfigured, landing alongside the move. **Backlog lines (not this session):** FinanceSettingsPage split (Stripe settings UI into the plugin via the admin socket — a natural P5+ rider that would also exercise surfaces 3/4), the EventController↔Portal paid-branch duplication, `products.stripe_product_id` dead column, the dead `events/show.blade.php` legacy view, missing e2e checkout coverage, no tests for `refund.created` / `payment_intent.payment_failed`.
9. **Vanish semantics (the remove-the-line guarantee, extended to a foundation plugin):** with the Payments line removed from `config/plugins.php` — webhook route 404s, all checkout endpoints return the existing "not configured" responses (because `enabled('payments')` is false when nothing provides it), the price observer never fires, `services.stripe.*` config is unpopulated, and the free/$0 paths work untouched. Proven by tests using the 379 SocketProbe two-file pattern (enabled twin via a config-appending TestCase where needed, removal mirror on the plain TestCase — note the shipped list DOES carry Payments, so the mirror here strips rather than appends; the session picks the clean mechanism and logs it).
10. **Contract doc at close:** surface 13 recorded with the registry mechanics and promoted to **PROVEN** (real shipping consumers: five vertical call sites + the dashboard widget; the honesty rule is satisfied by a shipped extraction, unlike 379's fixture). Surface 1's entry notes the second shipping plugin. Surface 10 gains the named P5 inversion plan. Version bump + changelog per the doc's discipline.
