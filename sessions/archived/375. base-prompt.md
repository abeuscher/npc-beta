## Process rules for every session

Base-prompt process rules apply in full (`sessions/template-base-prompt.md` § Process rules for every session). Session-specific:

- **The CSP does not weaken. This is the fixed constraint.** `'unsafe-eval'` does not enter the public `script-src` — the owner considered and rejected it. The admin carve-out (Filament needs eval) stays exactly as it is. If some widget behavior genuinely cannot be expressed under the CSP-compatible pattern, the answer is to rewrite that behavior, not to loosen the policy.
- **Audit before migrating.** The Open Gate presents the full Alpine inventory (which templates, which expression shapes, which are trivial vs. genuinely stateful) and the per-widget disposition — CSP-build registered component vs. plain-JS rewrite vs. CSS-only — before any template is edited. Don't discover the inventory mid-migration.
- **Verify the CSP build's actual constraints empirically before committing to it** (`@alpinejs/csp` allows only registered-component references and simple property/method access — no inline object literals, no inline statements, no comparisons in bindings; confirm how component parameters are passed, e.g. via `data-*` attributes read in `init()`). A 20-minute local spike on one widget beats discovering a blocker at widget nine.
- **Behavior parity per widget is part of "correct."** The nav dropdown's keyboard handling (escape-to-close, focus return — session 334 lineage), the custom select's a11y, the donation form's interactivity: each migrated widget is verified to *work*, not just to stop erroring. The e2e/Playwright surface and `bin/console-audit.mjs` are the tools.
- **Production is the finish line.** The success criterion is a zero-issue `console-audit` run against **https://nphelper.com** after deploy — plus a broader local page set (blog post, event landing page with the registration widget, donation page, portal sign-in, a page with each migrated widget placed) since the marketing pages exercise only a fraction of the widget inventory. The owner merges and deploys; you verify after. Bump VERSION first.
- **Rule 11 applies.** If the inventory is larger than one context can migrate well, split iterations at a clean widget boundary (e.g. `/1` = bundle + nav + the marketing-page widgets, `/2` = the rest + standing guards + deploy verification). Each iteration independently green.
- **Do not touch:** the admin panel's Alpine/Filament stack; the FM `/api/*` surface; the 374 events/email work; the page-builder Vue app (separate bundle, admin-side).
