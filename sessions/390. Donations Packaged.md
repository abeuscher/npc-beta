## The redraw input (ground truth, captured at 389 close)

**The four tables and their FK web (from `database/schema/pgsql-schema.sql`):**

1. **`funds`** — no outbound FKs; `funds_code_unique` on `code`. Create first.
2. **`donations`** — FKs: `contact_id` → contacts (SET NULL), `organization_id` → organizations (SET NULL), `fund_id` → funds (SET NULL), `import_source_id` → import_sources (SET NULL), `import_session_id` → import_sessions (SET NULL). Plugin→core FKs are legitimate (surface 5); the `fund_id` FK is plugin-internal.
3. **`donation_credits`** — FK `donation_id` → donations (CASCADE); the `attributable` morph carries no FK. Create after donations.
4. **`donation_receipts`** — FK `contact_id` → contacts (**RESTRICT** — this FK *is* the "blocks contact force-delete when receipts exist" behavior; it travels with the table and the behavior net must still pass). Create last.

**No core table carries an FK into any of the four** (verified 389) — the redraw severs nothing inbound; transactions reach donations only through polymorphic subject columns (strings, no constraint).

**Migration creation order: `funds` → `donations` → `donation_credits` → `donation_receipts`.** Author each as raw `DB::unprepared` DDL copied byte-faithfully from the dump (CREATE TABLE + defaults + indexes + the ALTER TABLE constraint statements), the 383 pattern exactly.

**Core reads of the four tables (the composition-safety survey — what the donations-absent identity check will exercise):**

- `SetupChecklist::checkDefaultFund()` — **unconditional `Fund::query()->exists()`**; runs on the dashboard setup widget. The likeliest 390 find (the `PageContextTokens` analogue).
- `Contact` model — `donations()` relation, `hasDonations()` (`exists()` call), two donor scopes (`whereHas('donations')`); reached from ContactResource list filters and delete/scrub paths (`ContactResource` line ~278), and `OrganizationResource`'s delete summary counts.
- `RandomDataGenerator` — donation scrub counts/creates (super-admin/dev tool; 383 treated the events analogue as accepted admin-only debt).
- `ContractResolver` — the `fund` (line ~132) and `donation` (~386) arms; core engine by design. `widgets:sync` drops the two widget rows on an absent composition, so no shipped page reaches the arms — same posture the `event` arm proved at 383.
- `TransactionResource` — subject-type label map + `$subject?->fund?->name`; lazy, reached only through existing donation transaction rows (none exist on a never-installed composition).
- `ImportSessionPreview` / `ImportSessionActions` — donation reads gated on `model_type === Donation`; safe by the same argument.
- The base seed writes **no** rows to any of the four tables (the surface-7 email rows are `email_templates`, core).

**Fixtures with the expiring caveat:** `DonationsRemovedTestCase` + `DonationsDisabledViaFlagTestCase` register no migrator path today; after the redraw both must register `plugins/Donations/database/migrations` (the Events fixture pattern) so data-kept assertions keep their schema.

**Testsuite state:** `Donations` suite at `plugins/Donations/tests` (18 files; 99 fast + 1 slow) — unchanged this session; it re-points to the vendor path at 391.

The dump regeneration and migration authoring land in one commit.
5. **Identity checks are the session's oracle** (contract surface 5's recorded procedure, both runs verified): full composition byte-identical modulo migrations rows/sequence/`\restrict`; donations-absent composition boots + public/admin smoke clean with no donation tables. Also re-run the 348-procedure seeded-data spot verification on the full composition.
6. **Composition-safety dispositions (the flagged cluster — pause here if any reads differently):**
   - `SetupChecklist::checkDefaultFund()` — **gate it**: skip the fund row entirely when the funds admin route is absent (the route-name signal 389 already introduced there for the URL). A donations-absent install has no donation form or importer, so a "you need a fund" checklist row is noise; skipping the row is the honest composition behavior. (Alternative — `Schema::hasTable` — rejected: route presence is the established plugin-absence signal.)
   - `Contact` donor scopes / `hasDonations()` / resource delete-path reads — **leave unconditional, accepted composition debt** (they run inside admin flows that only execute against existing data; on a never-installed composition the tables' absence only bites if the code path runs — the identity check's admin smoke decides whether any actually fires; gate only what the check surfaces, per the 383 fix-what-it-finds discipline).
   - `RandomDataGenerator` donation reads — **accepted admin-only debt** (the 383 events precedent, reaffirmed).
   - `ContractResolver` fund/donation arms — **stay core, ungated** (engine arms; rows dropped by sync — the proven `event`-arm posture).
7. **Schema docs annotated, not moved:** the four `docs/schema/*.md` files gain the plugin-owned header note (383 precedent); `docs/schema/README.md` notes the owner. Factories stay core (§ 6.7 — `DonationFactory`, `FundFactory`, `DonationReceiptFactory`).
