# Plugin Contract

**Contract Version:** `0.21.0`
**Status:** active — Stage D (full decomposition; eight extracted plugins VCS-resolved from their own repositories, `plugins/` empty until the next carve; the distribution manifest is the composed-set authority)
**Owner:** core (this repo). Plugins implement against this document.
**Canonical plan:** `sessions/plugin-architecture-plan.md` (architecture rationale, arc, question dispositions)

---

## What this document is

The single source of truth for the surface **core publishes to plugins**. A plugin is a self-contained module that extends core only through the surfaces listed here; core guarantees those surfaces and nothing else. An agent working inside a plugin should be able to substitute this document for core's code; an agent working in core must treat every PROVEN surface as a compatibility boundary.

**Marking discipline:** every surface below is marked **PROVEN** (exercised end-to-end by a shipped extraction, with tests) or **DECLARED** (specified, not yet exercised). A surface is only promoted to PROVEN in the session that exercises it. The version bumps FM-contract-style: additive clarifications bump the patch/minor version; changing a PROVEN surface's shape is a breaking change and bumps the major version once this doc reaches 1.0.0.

**Reference implementations:** the LogoGarden pilot (extracted from core session 377 — arc P1; moved to its own repository, `github.com/abeuscher/crm-plugin--logo-garden`, session 385 — arc P9, resolving into `vendor/nonprofitcrm/logo-garden/`) for a widget plugin, the Payments foundation plugin (carved session 380 — arc P4; moved to its own repository, `github.com/abeuscher/crm-plugin--payments`, session 387 — arc D1, resolving into `vendor/nonprofitcrm/payments/` — the first extracted foundation plugin and the first package owning a third-party dependency, `stripe/stripe-php`) for a non-widget plugin owning services, an HTTP surface, an observer, and a capability declaration, and the Events vertical (carved session 381 — arc P5; moved to its own repository, `github.com/abeuscher/crm-plugin--events`, session 388 — arc D2, resolving into `vendor/nonprofitcrm/events/` — the first extracted plugin owning its schema migrations and carrying its own testsuite) for a full domain vertical: public + portal controllers and routes, observers, policy, mailables, a scheduled command, a Filament resource + import pages through the admin socket, seven widgets (nested under `Widgets/`), an importer contribution, and an optional foundation-plugin dependency consumed through capability detection. The Donations vertical (carved session 389 — arc D3; moved to its own repository, `github.com/abeuscher/crm-plugin--donations`, session 391 — arc D3, resolving into `vendor/nonprofitcrm/donations/`) is the second full-vertical reference: the second extracted migration-owning, testsuite-carrying plugin, the first contributor to the email-template registry (surface 7), and the fulfillment side of the first cross-repo inversion (surface 10).

## In-repo plugin shape (Stage A)

```
plugins/{PascalName}/
    {PascalName}ServiceProvider.php   ← the single entry point
    ...everything else the plugin owns
```

- **Location:** top-level `plugins/{PascalName}/`.
- **Namespace:** `Plugins\{PascalName}\`, autoloaded via the `"Plugins\\": "plugins/"` PSR-4 entry in `composer.json`.
- **Wiring:** one line in `config/plugins.php` — an ordered list of plugin service-provider class strings, registered at bootstrap by core's `App\Providers\PluginServiceProvider` (listed in `bootstrap/providers.php` after `WidgetServiceProvider`, so core singletons exist before any plugin boots). **Remove the line and the plugin is gone**: no registration, no views, no synced `widget_types` row on the next `widgets:sync`. This list was designed as the in-repo miniature of the distribution-manifest / per-install-activation layer — since session 386 it is the **generated artifact** of the real thing, `distribution.json` (see The distribution manifest; edit the manifest, not this file).

## Package shape (Stage B)

A Stage B plugin keeps the Stage A shape and folder location and additionally becomes a real composer package resolved through a path repository (first shipping example: `nonprofitcrm/logo-garden`, session 382 — arc P6; second consumer: `nonprofitcrm/events`, session 383 — arc P7, the first packaged domain vertical, carrying its own `database/migrations/` and `tests/`; third: `nonprofitcrm/payments`, session 387 — arc D1, as the extraction walk's `path` step; fourth: `nonprofitcrm/donations`, session 390 — arc D3, packaged with its own `database/migrations/` and `tests/` ahead of its extraction at 391; fifth: `nonprofitcrm/memberships`, session 393 — arc D4, packaged and extracted in the same session on the D1 compression precedent; sixth: `nonprofitcrm/member-portal`, session 395 — arc D5, the same one-combined-session shape; seventh: `nonprofitcrm/blog`, session 396 — arc D6, the first packaged vertical owning **no schema** — posts are core `Page` rows, so the package carries no `database/migrations/`; eighth: `nonprofitcrm/forms`, session 397 — arc D7, packaged with its own `database/migrations/` and `tests/` in the same session as its carve and extraction; as of session 391 every shipping plugin has moved through this shape to External repo below, so the path-repo stage is currently the transitional middle of each carve → package → extract block):

```
plugins/{PascalName}/
    composer.json                     ← name, "type": "library", explicit "version",
                                        PSR-4 "Plugins\{PascalName}\": "", PHP constraint
    {PascalName}ServiceProvider.php   ← still the single entry point
    ...everything else the plugin owns
```

- **Resolution:** the root `composer.json` carries a `path` repository entry for the plugin folder and a bound version requirement; `composer install` symlinks `vendor/{vendor}/{package}` → the plugin folder. The package declares an explicit `version` field so resolution is deterministic everywhere the build runs without git metadata (the Docker image build excludes `.git/`).
- **Activation and ordering stay with `config/plugins.php`** — see surface 1. The package declares **no** `extra.laravel.providers`; Laravel auto-discovery is deliberately unused.
- **PSR-4 overlap (accepted, documented):** the root `"Plugins\\": "plugins/"` mapping still covers every in-repo plugin; a packaged plugin's own PSR-4 maps the same files. Both mappings resolve to identical paths, composer tolerates the overlap, and the root mapping retires per-plugin as each becomes a package.
- **Image builds:** plugin package manifests are part of the Dockerfile's manifests-before-source layer set — `plugins/{PascalName}/composer.json` is copied before both `composer install` layers so the path repository resolves while layer caching (source edits never bust the dependency layers) is preserved; the install-time symlink resolves fully once the full source lands. **One `COPY` line per packaged plugin, per stage** — never a glob: Docker `COPY plugins/*/composer.json` flattens the directory structure (the P6 caveat, applied at P7).
- **Third-party dependencies are package-owned (session 387 — arc D1):** a plugin that uses a third-party library declares the require in **its own** `composer.json`; the root manifest drops its direct line in the same commit, and the lock must resolve the identical version (now transitive). First shipping example: `nonprofitcrm/payments` owns `stripe/stripe-php ^16.6` (root's direct require dropped, lock resolution unchanged at v16.6.0). This is the pattern for every dependency-carrying plugin. Boundary guards are unaffected by design — they ban SDK *use* outside the plugin, not the package's presence in the lock.
- **Core dependency modeling** (the package requiring core at composer level) is deliberately absent at P6 — the package programs against this contract; modeling the dependency is P7+ territory.

## External repo (Stage C-lite)

A Stage C plugin keeps the Stage B package shape but lives in **its own repository** (first shipping example: `nonprofitcrm/logo-garden` at `github.com/abeuscher/crm-plugin--logo-garden`, session 385 — arc P9; second: `nonprofitcrm/payments` at `github.com/abeuscher/crm-plugin--payments`, session 387 — arc D1, the first extracted foundation plugin, whose consumers reach it only through the core-owned capability layer of surface 13 — extraction required no edit outside the plugin beyond re-pointing three test file reads; third: `nonprofitcrm/events` at `github.com/abeuscher/crm-plugin--events`, session 388 — arc D2, the first extracted plugin owning schema migrations and carrying its own testsuite, whose extraction emptied `plugins/` entirely; fourth: `nonprofitcrm/donations` at `github.com/abeuscher/crm-plugin--donations`, session 391 — arc D3, the second migration-owning, testsuite-carrying extraction — the D2 postures re-proven on a second consumer with no new edges, emptying `plugins/` again until the next carve; fifth: `nonprofitcrm/memberships` at `github.com/abeuscher/crm-plugin--memberships`, session 393 — arc D4, the third migration-owning, testsuite-carrying extraction, run in the same session as its packaging on the D1 compression precedent, emptying `plugins/` a third time; sixth: `nonprofitcrm/member-portal` at `github.com/abeuscher/crm-plugin--member-portal`, session 395 — arc D5, the fourth migration-owning, testsuite-carrying extraction, packaged and extracted in one session, emptying `plugins/` a fourth time; seventh: `nonprofitcrm/blog` at `github.com/abeuscher/crm-plugin--blog`, session 396 — arc D6, carved, packaged, and extracted in one session — the first extraction with **no owned schema** (the twin fixtures permanently register no migrator path; blog-absent, the page-slug catch-all still serves post rows as plain pages — listing-absent, not page-absent), emptying `plugins/` a fifth time; eighth: `nonprofitcrm/forms` at `github.com/abeuscher/crm-plugin--forms`, session 397 — arc D7, the second single-session carve → package → extract run and the fifth migration-owning, testsuite-carrying extraction, emptying `plugins/` a sixth time; repo naming pattern `crm-plugin--{kebab-handle}`), consumed exactly like the Fleet Manager relationship: separate repo, tagged versions, this contract doc programmed against on both sides, changes contract-first. The repeatable procedure is `docs/plugin-extraction-runbook.md`.

- **Resolution:** the root `composer.json` swaps the plugin's `path` repository entry for a **`vcs`** repository entry at the GitHub URL; the require stays bound (`^0.1`). The lockfile pins the tag: a git source at the exact tag commit plus a dist zip of it. `composer install` fetches the package — no source `COPY` lines in the Dockerfile, and no path back into the core repo.
- **The `version` field inverts:** the extracted package declares **no** explicit `version` in its `composer.json`. That field was the *path-repo* determinism device (resolution without git metadata); under a VCS repository **git tags are the version metadata**, and a retained field that disagrees with the tag is a composer install error. Tags are releases; core bumps its lock deliberately (`composer update {vendor}/{package}`).
- **Auth posture:** the plugin repo is **public**, so `composer install` stays credential-free in every context that builds the image (CI tests job, CI e2e image build, GHCR deploy build, a fresh machine). A private plugin repo would require composer credentials in all of those contexts — audit them before choosing private.
- **Asset paths are vendor-relative** (`vendor/{vendor}/{package}/…`) — see surface 11.
- **What stays identical:** the provider remains the single entry point; the `config/plugins.php` line, activation ordering, and the derived handle are unchanged (activation is namespace-keyed and location-independent — the surface-1 guarantees, including `PLUGINS_DISABLED` and remove-the-line, are proven against the vendor'd package by the same tests, assertions unchanged). The root `"Plugins\\"` PSR-4 overlap **retires for the extracted package** — its own PSR-4 mapping is now the only one covering it.
- **Guards follow the code:** every standing guard that scans `plugins/*` also scans extracted packages via the shared `extractedPluginPackageDirs()` test helper (non-symlink dirs under `vendor/nonprofitcrm/*` — path-repo symlinks are skipped so nothing is scanned twice). `PluginPackageGuardTest` pins the extracted shape: lock-pinned to a tag-shaped version at an exact commit, dist zip, no manifest `version` field, still no auto-discovery.
- **Test membership at extraction (amended session 388 — two postures):** tests whose files already live **inside** the plugin travel with the package, and the core repo's phpunit testsuite re-points to the vendor path (`vendor/{vendor}/{package}/tests`) so core CI runs the same files unchanged — the plan § 6.3 "central build runs the distribution's plugin suites" disposition made real (first consumer: the `Events` suite, 29 files, identical counts from the vendor path under paratest and CI; second: the `Donations` suite, session 391 — 14 files, 103 fast + 1 slow, identical counts). Core-side *subject* tests for a plugin that never carried its own suite stay in the core repo (the session-384 owner ruling — LogoGarden, Payments). Per-plugin CI in the plugin repo (core as a dev dependency) remains the standing follow-up (arc D11).
- **An extraction may empty `plugins/` entirely** (session 388 — Events was the last in-repo plugin). Guards that scan or assert on the in-repo set must tolerate its absence — git tracks no empty directories, so `plugins/` vanishes from a fresh checkout — while the extracted-package roots keep every zero-allowlist guarantee covering the plugin code. The root `"Plugins\\": "plugins/"` PSR-4 mapping stays (its retirement is the D12 endgame; the next vertical carve refills `plugins/`).

## The distribution manifest (Stage C-lite, session 386)

**`distribution.json`** at the repo root is the authority for which plugins a build composes and in what order — the layer the config list was always the miniature of (plan § 4d). One committed file, one distribution ("this repo's composition"); per-niche distribution repos and per-distribution composer sets are **Stage E — deliberately not built**. Per plugin entry:

- **`provider`** — the service-provider FQCN. **Array order is the provider load order** (the ordering authority lives here).
- **`source`** — how composer resolves the plugin, modeled honestly: `folder` (a plain in-repo folder on the root `"Plugins\"` PSR-4 — not a composer package; Payments' shape until D1), `path` (in-repo package via a root path repository; carries `path`), or `vcs` (external repository; carries `url`).
- **`package` + `constraint`** — the composer package name and bound version requirement, present exactly when the source kind is `path` or `vcs` (a `folder` entry declaring them is a validation error — the manifest never pretends).

**`config/plugins.php` is a generated artifact**: `php artisan plugins:manifest-sync` writes it from the manifest (single reader: `App\Plugins\DistributionManifest`), deterministically and byte-stably, with a generated-file header. The file stays committed and the runtime loader still reads it — no bootstrap-time JSON parsing; every surface-1 guarantee (ordering, subtraction-only activation, remove-the-line) survives generation verbatim. **Remove-the-entry ≡ remove-the-line by construction** — deleting a manifest entry and regenerating removes the provider line, and with it the plugin's entire composed surface on the next build. A malformed manifest throws naming the problem (the unknown-handle fail-loud posture, one level up).

**Hand-maintained surfaces are guard-pinned, not generated.** `composer.json` (repositories + requires) and the Dockerfile (manifests-before-source COPY lines) stay hand-maintained; the standing guard `DistributionManifestGuardTest` asserts alignment — regeneration idempotence (a stale or hand-edited config list fails the suite), lock-pinning per declared source kind, repository/require agreement with the manifest, and **no unmanifested plugin surfaces** (`nonprofitcrm/*` lock packages, `plugins/` directories, Dockerfile plugin-COPY lines, `plugins/` phpunit testsuites all trace back to manifest entries). `PluginPackageGuardTest`'s extracted set derives from the manifest's vcs-sourced entries — an extraction is declared once, in the manifest.

**Scope boundary (recorded, not built):** at P10 a manifest edit changes what the built image *registers, migrates, and syncs* — the composed set. The package code of a removed entry may still ship in the image, inert (composer.json is hand-maintained and unchanged). True per-distribution code absence ("not in the niche image at all", changeability tier 2's strong form) arrives with Stage E's per-distribution composer sets.

## The 13 surfaces

### 1. Registration — **PROVEN** (session 377; two-layer activation model session 384)

One service provider per plugin, registered by core's `PluginServiceProvider` during bootstrap. Activation is **two-layered** (session 384, arc P8):

- **Installed** = in the image: **the distribution manifest's set** (amended at session 386, arc P10). `distribution.json` is the authority for the installed set and its order; `config/plugins.php` is generated from it (`plugins:manifest-sync` — see the distribution-manifest section above) and remains what the runtime loader reads, the superset and **sole runtime ordering authority** (amended at session 382, superseding the earlier "Stage B replaces the config list with package auto-discovery" posture): packages declare no `extra.laravel.providers` and Laravel auto-discovery is deliberately unused, because the remove-the-line guarantee, the registries-before-plugins binding order, and plugin-boot-before-core-routes ordering are all load-bearing and all keyed on the config list — auto-discovery would move activation to composer edits and surrender ordering to installation order. Generation preserves those guarantees verbatim (same FQCNs, manifest order); removing a manifest entry and regenerating **is** removing the line. The provider remains the single entry point at every stage.
- **Enabled** = installed minus the per-install disabled set: `PLUGINS_DISABLED`, a comma-separated list of plugin handles read from `.env` through `config/plugin-activation.php` (config-cache-safe; env-backed by design — registration happens at bootstrap, before the database is guaranteed to exist, and `.env` is what FM's config-push channel delivers per install). `PluginServiceProvider::register()` filters the config list by the disabled set before registering — **subtraction only, never reordering, never adding**; unset/empty means every installed plugin runs. The registries-before-plugins binding order and every surface-4 ordering guarantee survive the filter unchanged for the plugins that remain.

**Handles are derived, not declared:** kebab-case of the plugin's PascalName namespace segment, computed from the provider FQCN (`Plugins\LogoGarden\…` → `logo-garden`, `payments`, `events`) — no registry, deterministic, matches the composer package names (`PluginServiceProvider::handleFor()`).

**Unknown handles fail the bootstrap** (strict posture, security-over-usability): a handle in `PLUGINS_DISABLED` matching no installed plugin throws at registration with a message naming the bad handle and the valid set — a silently ignored typo would leave a plugin running that the operator meant to disable. Failure is caught immediately by the image healthcheck / `compose up --wait` / the deploy pipeline. Disabling an already-disabled handle is idempotent (set semantics).

**Runtime-disabled ≡ strip-the-line, by construction.** The filter subtracts at the exact seam the `RemovedTestCase` fixtures prove (same list, same subtraction, earlier actor), so a runtime-disabled plugin produces precisely the state the removal mirrors assert: provider not loaded, routes gone, no schedule, no admin pages, widget rows dropped on the next `widgets:sync`, **data and schema kept** (normative rule 4), other plugins untouched. Disabling stops registration — nothing deletes, migrates down, or mutates plugin data.

**The tier-1 flip runbook** (per-install; verified end to end in the session-384 superset-image run — one built image, compositions chosen per install by the flag and nothing else):

1. Edit `PLUGINS_DISABLED` in the install's `/opt/nonprofitcrm/.env` (e.g. `PLUGINS_DISABLED=events`; empty to enable everything).
2. Recreate the containers so the new env is read — `docker compose -f docker-compose.prod.yml up -d` (`.env` is read at container *start*; the `worker` needs the same restart) — then `php artisan config:clear` to drop any cached config.
3. **When enabling** a plugin whose migrations have never run on this install: `php artisan migrate --force` — the plugin's pending migrations apply then (surface 5's install order; on installs where the plugin ran before, its schema and data are already present and `migrate` is a no-op).

FM's config-push channel is the intended delivery mechanism for step 1; the FM side (and any plugin manifest in `/api/health`) is a future FM-contract item.

**A plugin may own an auth guard (session 394 — arc D5).** The MemberPortal plugin injects the `portal` guard, its `portal_accounts` user provider, and the `portal_accounts` password broker into `config('auth.*')` from its provider's `register()` (the Payments `services.stripe` config-injection posture applied to auth config — static values, so no DB guard is needed and the injection precedes any request-time guard resolution). `config/auth.php` keeps no portal entries. Consequence, binding on core: on a composition without the plugin the guard name is **undefined and `auth('portal')` throws** — every core reach gates on the plugin's capability (surface 13) before touching the guard (session 394 gated the five shipping reads: `PageContext`, `PageController`'s member-page branch, `ActivityLogger`, `FormSubmissionController`'s collision check, and the `portal_member` resolver arm).

Proven by: `Plugins\LogoGarden\LogoGardenServiceProvider` — registered through the config list, asserted loaded in `tests/Feature/PluginPilotSession377Test.php`. Second shipping consumer (session 380): `Plugins\Payments\PaymentsServiceProvider`, the first non-widget plugin — its provider owns contract bindings and a capability declaration at `register()`, and config injection, an observer, and a route file at `boot()` (`PaymentsPluginSession380Test` + the removal mirror). The activation layer (session 384): unit coverage of derivation/subtraction/ordering/unknown-handle (`PluginActivationTest`), the flag-disabled vanish-equivalence mirror (`EventsDisabledViaFlagSession384Test` on its fixture), the any-set generalization incl. LogoGarden's first vanish coverage (`LogoGardenPaymentsDisabledViaFlagSession384Test`), and the superset-image verified run (one image, full + events-disabled compositions + the enable-later flip — session-384 log).

### 2. Widget contribution — **PROVEN** (session 377)

A plugin registers `App\Widgets\Contracts\WidgetDefinition` subclasses into the core `App\Services\WidgetRegistry` singleton from its provider's `boot()`. The registry API is core-owned and unchanged; `widgets:sync` remains the only writer of `widget_types` rows and is idempotent regardless of where a definition registers from.

- **Views:** the plugin registers its own Blade namespace in `boot()` (pilot: `plugin-logo-garden::`, pointing at the plugin folder) and overrides `template()` to include through it. The shared `widgets::` namespace (→ `app/Widgets`) stays core-only.
- **Blade components (session 397 — arc D7, the first plugin-owned component):** a plugin whose render surface is a Blade component registers it from `boot()` via `Blade::anonymousComponentPath()` pointing at the plugin's components directory — the tag resolves **unprefixed**, so a component lifted out of core keeps its exact tag (`<x-public-form>`, formerly `resources/views/components/`, now the Forms plugin's `resources/views/components/`) and every consumer renders it byte-identically. Like core Blade components, a plugin-owned component is view infrastructure and sits outside the surface-2 template-purity scan (it is not a `template.blade.php`); the purity rule still binds the widget *templates* that consume it. Unprefixed registration is namespace-squatting-capable by construction — a plugin must only register component names it owned at carve time or introduces itself.
- **Thumbnails:** core resolves a widget's thumbnail directory via `WidgetDefinition::thumbnailDir()` — derived by reflection from the concrete definition class's own file location, so it holds in core and in plugins with no override. Ship `thumbnails/static.png` (and `preset-*.png`) next to the definition; `scripts/generate-thumbnails.js` writes to whichever of `app/Widgets/{Name}/` or `plugins/{Name}/` exists.
- **Data access (ENFORCED, session 378 — arc P2):** widget templates are pure renderers — they read only `$config` / `$configMedia` / `$widgetData` / `$pageContext` and render-layer helpers. No model calls, no `auth()`, no `app()`/`resolve()`/`@inject`, no `DB::`/`Auth::` in any template. The standing guard `tests/Feature/WidgetTemplateBoundaryTest.php` scans `app/Widgets/*/template.blade.php`, `plugins/*/template.blade.php`, and `resources/views/widget-shared/*` and fails on any such reach, with **no allowlist**. Core Blade components (`<x-picture>`, `<x-widget-buttons>`, …) are core view infrastructure and outside the scan.
- **Declaring contracts:** the singular `dataContract(array $config): ?DataContract` remains the common case. Widgets consuming several sources override `dataContracts(array $config): array` — named contracts (`['event' => …, 'member' => …]`); their templates receive `$widgetData` keyed by contract name, while single-contract widgets keep the unkeyed `['items' => …]` / `['item' => …]` shape. User query-config merges into the primary (first) contract only.
- **Sources & arms (exercised by the P2 retrofit):** `SOURCE_SYSTEM_MODEL` arms now include `fund`, `membership_tier`, `navigation_menu` (single, id filter), and `portal_member` (single; resolves the portal guard inside the arm, logged-out ⇒ `['item' => null]`, non-leak tested). `SOURCE_SERVICE` covers service-backed datasets (`setup_checklist`, `scrub_counts`) whose arms hard-gate on super-admin. `SOURCE_PAGE_CONTEXT` contracts may declare fields (e.g. `site_name`, a site-global token) for direct `$widgetData` reads. Every arm projects contract-declared fields only, fail-closed.
- **Widget folder paths:** `WidgetDefinition::baseDir()` resolves the widget's own folder by reflection (generalizing 377's `thumbnailDir()`); anything declared relative to the widget folder (thumbnails, screenshots) resolves through it in core and plugins alike.

**At-scale contributor (session 381):** the Events vertical registers seven widgets from one provider, nested at `plugins/Events/Widgets/{Name}/` (a vertical plugin's widget folders nest under `Widgets/`; single-widget plugins stay at the plugin root). Each definition overrides `template()` to include through the plugin's own widget view namespace, and template partials (`event-row`, `row`) include through the same namespace. Standing-guard globs (`WidgetTemplateBoundaryTest`, `WidgetColorTokenConsumptionTest`) and the thumbnail tooling cover the nested shape. `widgets:sync` keeps the seven `widget_types` rows (handles unchanged) with updated asset paths; a plugin widget may declare a **core-owned** stylesheet as a build input (EventsListing and BlogListing both declare `resources/scss/widgets/_shared-pager.scss` — the shared pager bar, lifted core-side at session 396 per ADR 0007 when its former home, the BlogPager widget folder, left core) — asset paths are repo-relative build inputs, not namespace reaches.

Proven by: the pilot's registration, sync-row, and view-namespace tests (`PluginPilotSession377Test`), render parity through the contract resolver (`LogoGardenContractRetrofitTest`), the all-41 retrofit's arm + parity tests (`WidgetBoundaryArmsSession378Test`, `WidgetBoundaryRetrofitSession378Test`), and the standing boundary guard (`WidgetTemplateBoundaryTest`).

### 3. Admin contribution — **PROVEN** (session 381)

A plugin declares its admin-shell contribution from its provider's `register()` by handing an `App\Plugins\AdminContribution` to the core `App\Plugins\PluginAdminRegistry` singleton (bound by `PluginServiceProvider` before any plugin registers; `AdminPanelProvider` reads the registry when Filament builds the panel — `bootstrap/providers.php` guarantees the ordering). The contribution declares:

- **Filament discovery paths** — `resourcesPath`/`resourcesNamespace` and `pagesPath`/`pagesNamespace`, joined to core's own `discoverResources`/`discoverPages` calls. `null` = the plugin contributes nothing on that axis.
- **Permission names** — seeded by core's `PermissionSeeder` (idempotent `firstOrCreate`, guard `web`) wherever core permission seeding runs; "enabled" in Stage A = listed in `config/plugins.php`. Granted to **no shipped role** — super-admin reaches via the `Gate::before` bypass (the `manage_account` precedent). Disabling a plugin stops the seeding but never deletes seeded rows (disabled-is-inert rule: they remain, gating nothing).
- **An in-panel route file** — see surface 4.

Three settled conventions (owner-approved, session 376), now mechanical:

1. Core owns the nav-group list (the five `->navigationGroups()` entries in `AdminPanelProvider`, the single source). A plugin's pages join a group with Filament-native `$navigationGroup` — which **must** name a core group; no plugin-invented groups in Stage A — and order themselves with `$navigationSort`.
2. A plugin declares its permissions in its registry entry; core seeds them at enable time, granted to no shipped role by default except super-admin.
3. Plugin admin pages inherit core's admin theme — plugins ship no admin CSS. **Enforced** by the standing guard `tests/Feature/PluginAdminCssGuardTest.php`: no `.css` files under `plugins/`, no `viteTheme`/render-hook stylesheet injection in plugin PHP. Widget-scoped SCSS/JS (surface 11) is legitimate and does not trip it.

Removing the plugin's `config/plugins.php` line removes the whole contribution — page, routes, permission seeding (the surface-1 remove-the-line guarantee, extended to the admin socket).

**Extracted-vertical permission nuance (session 381):** the permission channel above is for genuinely NEW permission names a plugin introduces. A vertical extracted from core keeps its pre-existing resource permissions (e.g. `view_any_event` … `delete_event`) in core's `PermissionSeeder` role matrix with their shipped-role grants — moving their seeding to the plugin channel would break the role matrix on a plugin-removed install (Spatie throws granting a missing permission). Core's role matrix stays whole until it becomes composable (arc P8 at the earliest); the Events plugin accordingly declares **no** permission names.

Proven by: the Events vertical (session 381, arc P5) — `EventResource` + four pages plus the two import wizard pages discovered from `plugins/Events/Filament/` via `resourcesPath`/`pagesPath`, landing on byte-identical route names/URIs/middleware (272/272 parity, action FQCNs excepted), nav placement (`CMS` group, sort 3) unchanged. The `SocketProbe` fixture (+ removal mirror) is **kept as a standing regression fixture** — it exercises the socket in isolation, including axes no shipping plugin currently uses. Removal mirror: `EventsPluginRemovalSession381Test` (admin resource + import pages gone).

### 4. Routes — **PROVEN** (session 381)

Core's own admin routes are the precedent: `AdminPanelProvider`'s former ~100-line inline `->routes()` closure is decomposed into per-feature files under `routes/admin/` (session 379, route-list parity verified) — each file self-contained, carrying its own middleware/prefixes/names, pulled into the panel's route group.

A plugin contributes the same shape: the `routesFile` path in its `AdminContribution` is pulled into the panel's `->routes()` group after core's files. **Core wraps every plugin pull in Filament's `Authenticate` middleware — a plugin admin route can never opt out of panel auth**; the plugin's file carries everything else (names, prefixes, extra middleware). Routes land inside the panel's base middleware stack (suspension gate, security headers, session, CSRF) and under the panel's name prefix (`filament.admin.`).

Front-of-house (non-panel) routes are the other half of this surface: a plugin's provider `loadRoutesFrom()`s its own route file, self-contained with middleware and names (the Payments webhook precedent, session 380). Provider `boot()` runs before core's `routes/web.php` loads (at app booted), so a plugin GET route registers ahead of the page-slug catch-all — the Events JSON endpoint depends on this ordering. At scale: the MemberPortal plugin registers the whole 17-route portal surface this way (session 394 — GET pages under the `system_prefix`, root-path POSTs, throttles, the `signed` verification link), names/URIs/middleware byte-identical to the pre-carve core registrations.

**A plugin may own a middleware alias (session 394 — arc D5, the first).** The MemberPortal provider registers `portal.auth` via `Route::aliasMiddleware()` in `boot()`; core's `bootstrap/app.php` carries no portal alias. Aliases resolve at **dispatch**, not registration, so ordering against route files that reference the alias doesn't matter — but a route referencing an alias that no enabled plugin registers **500s at dispatch instead of vanishing**. A sibling plugin that rides another plugin's middleware alias must therefore gate its route registration on that plugin's capability (surface 13 — the `crm-plugin--events` v0.1.2 posture: `portal.events.register` registers only when `member-portal` is present, so a portal-absent composition answers 405/404 from the catch-all rather than erroring).

Proven by: the Events vertical (session 381) — `plugins/Events/routes/web.php` registers `events.register` (throttled POST), `portal.events.register` (portal-auth stack), and `api.events.json` (GET ahead of the catch-all) with identical names/URIs/middleware to their pre-carve core registrations; admin-page routes land through surface 3's discovery. The `routesFile` in-panel pull specifically remains exercised by the standing SocketProbe fixture (no shipping plugin needs an in-panel route file yet). Vanish: with the line removed the POST paths answer 405 (the GET catch-all owns every path) and the JSON path falls to the catch-all as 404 (`EventsPluginRemovalSession381Test`).

### 5. Migrations — **PROVEN** (session 383)

`loadMigrationsFrom` per plugin, registered in the provider's `boot()`. The squash boundary (redrawn session 383, arc P7 — plan doc §6.7): **core's schema dump covers core tables only**; a plugin's tables live in its own `database/migrations/` as create-table migrations authored byte-faithfully from the dump DDL they replaced (raw `DB::unprepared` statements — pg_dump round-trips its own output, so the identity check below diffs clean; schema-builder calls would risk expression-normalization drift in check constraints). First shipping consumer: `plugins/Events/database/migrations/` creating `events` → `ticket_tiers` → `event_registrations` (FK order), including FKs into core tables — plugin→core FKs are legitimate; the plugin owns the tables, not isolation from core's schema. Second consumer (session 390, arc D3): `plugins/Donations/database/migrations/` creating `funds` → `donations` → `donation_credits` → `donation_receipts` — the largest FK web yet (five plugin→core FKs plus two plugin-internal ones) and the first redraw where **a moved FK is itself a behavior**: `donation_receipts.contact_id` is `ON DELETE RESTRICT`, and that constraint *is* the blocks-contact-force-delete-while-receipts-exist behavior — it travels with the table, and the behavior net must still pass against the plugin-owned schema. A moved table's sequences travel too (`donation_receipts_id_seq`: `CREATE SEQUENCE`, `OWNED BY`, and the `SET DEFAULT nextval` statement all move with the create-table migration). Third consumer (session 393, arc D4): the Memberships package creating `membership_tiers` → `memberships` — the smallest redraw yet (zero inbound FKs from any core table), the second RESTRICT-FK-as-behavior case (`memberships.contact_id` — the blocks-contact-force-delete net rides the plugin-owned schema unchanged), and **the first redraw with no sequences** (both PKs are uuid — the sequences-travel-too category can be empty; record it as such rather than skipping silently). A base-seed row can be plugin-owned too: core's `DatabaseSeeder` gates its `MembershipTierSeeder` call on the plugin-presence signal (route presence), so a memberships-absent composition seeds no tier row and touches no membership table. Fourth consumer (session 395, arc D5): the MemberPortal package creating `portal_accounts` → `portal_password_reset_tokens` — the **second sequence-carrying redraw** (`portal_accounts_id_seq` travels complete, the `donation_receipts_id_seq` mechanics) and the first with a **SET-NULL FK as the moved behavior** (`portal_accounts.contact_id` is `ON DELETE SET NULL` — a contact force-delete orphans the account row rather than blocking; plain referential behavior, travels as-is, no behavior net required). **Seeded topology is composition-scoped too** (the seeder-gate note, generalized): a plugin's *page* topology — not just its table rows — vanishes with it. Core's `DatabaseSeeder` gates the `PortalPageSeeder` call and `SystemPageSeeder` gates its three portal auth pages on the `member-portal` capability (the surface-13 presence signal), so a portal-absent composition seeds neither the three member-type pages (404 shells behind the gated member branch) nor the three auth pages (empty of their plugin widgets) — while the seeder's site-wide chrome (header/footer) seeds on every composition. The per-composition identity check (b) arbitrates: its smoke expects clean catch-all 404s for the ungated slugs. **A vertical may own no schema at all (session 396 — arc D6, the Blog vertical):** posts are core `Page` rows of type `post`, so the package ships no `database/migrations/`, the squash-redraw phase is empty (recorded, not skipped — the 387/393 wording discipline), the twin fixtures **permanently** register no migrator path (their docblocks say so explicitly, not the expiring-caveat wording), and there is no mark-as-applied deployment step. The one schema event in that block was a plain core drop: the dead `posts` table (zero readers, zero rows — pre-dating the pages-as-posts CMS shape) left the dump via a guarded core migration with the 348-precedent identity check (the dump diff exactly the posts DDL). Vanish semantics invert on such a vertical: content is not plugin data — blog-absent, the page-slug catch-all still serves every post row as a plain page (listing-absent, not page-absent). Fifth consumer (session 397, arc D7): the Forms package creating `forms` → `form_submissions` — the **first redraw carrying two sequences** (`forms_id_seq` + `form_submissions_id_seq`, each traveling complete with its table: CREATE SEQUENCE + OWNED BY + SET DEFAULT nextval — the portal mechanics per table), the second SET-NULL-FK-as-plain-behavior case (`form_submissions.contact_id` — a contact force-delete orphans the submission row), and the first traveling **plugin-internal CASCADE FK** (`form_submissions.form_id → forms` — both tables plugin-owned, the constraint never touches core). Zero inbound core FKs. The seeder gate note's third consumer: core `DatabaseSeeder` gates its `FormSeeder` call on route presence (`Route::has('forms.submit')` — the tier-seeder precedent), so a forms-absent composition seeds no form rows.

- **Deterministic install order: core dump → enabled plugins' migrations → seeders.** A fresh `migrate` loads the dump, then runs each enabled plugin's pending migrations (their rows append to the shared `migrations` table); enabling a plugin later runs its migrations then — operationally, the surface-1 tier-1 flip runbook (flag off → container restart → `migrate`), verified end to end in the session-384 superset-image run. Playwright's e2e `migrate:fresh --seed` and CI cover the order on every push.
- **Two vanish semantics** (settled session 383): *disabled ≠ uninstalled*. **Disabled** = installed-then-disabled: activation stripped, schema present, **data kept** (normative rule 4). The strip-the-line fixtures model this by registering the plugin's migration path directly on the migrator (`EventsRemovedTestCase` — the provider never boots, the tables still exist, every data-kept assertion holds; since session 388 the fixtures register the **vendor** path, `vendor/nonprofitcrm/events/database/migrations` — the semantics survive extraction with assertions unchanged; second consumer session 391: the two Donations fixtures re-pointed to `vendor/nonprofitcrm/donations/database/migrations` at its extraction). **Never-installed** is a different *composition*: the tables simply never exist — proven by the per-composition identity check, never by per-test fixtures.
- **Per-composition fresh-install identity check** (verified runs, session-383 procedure): (a) *full composition* — fresh install must dump byte-identical to the pre-redraw reference, modulo the plugin's `migrations` rows + sequence value (and pg_dump's per-run `\restrict` token); plus the 348-procedure seeded-data spot verification. (b) *plugin-absent composition* — core dump + seeders boots clean, public + admin smoke pass, no plugin tables present. Regenerating the core dump: run `schema:dump` only against a database whose plugin tables were dropped first, and recreate the *database* rather than `DROP SCHEMA public` (a user-recreated `public` schema changes pg_dump's preamble). Standing guard: `PluginPackageGuardTest` pins plugin-owned tables out of the core dump and the plugin's create-table migrations present.
- **Core-model caveat:** core keeps the `Event`/`EventRegistration`/`TicketTier` models and factories (plan §6.7 — the model move is deliberately unscheduled), so core code reading a plugin-owned table must be composition-safe. Unconditional reads fail on a never-installed composition — gate them (the `PageContextTokens` page-type gate, session 383, is the precedent; `AppearanceStyleComposer`/`SeoMetaGenerator` already gated). Admin-only reaches (page-builder data sources, random-data generator) are accepted composition debt until the per-install activation layer (arc P8).

### 7. Email templates — **PROVEN** (session 389)

Handle registration replacing the hard-coded defaults array on `EmailTemplate` for plugin-owned handles. A plugin contributes `handle → defaults` (subject / body / footer_reason) to the core `App\Plugins\EmailTemplateRegistry` singleton from its provider's `register()` (bound by `PluginServiceProvider` before any plugin registers — the ImporterRegistry pattern). Two core consumers resolve through it:

- **`EmailTemplate::defaults()`** (the `forHandle()` firstOrCreate seed): core-owned handles stay in the model's own array; a handle the array does not carry falls back to the registry; an unknown handle still falls back to the empty template. Precedence is core array → registry → empty.
- **The base seeder** seeds one `email_templates` row per registry contribution after the core-handle rows — a composition without the plugin seeds no row for its handles, and `forHandle()` on such an install creates the empty template (writes stopped is not implicated; the handle's consumers are plugin code that is absent with it).

Contributions replace their core-array entries byte-identically at carve time — the admin-edited row always wins (`firstOrCreate` semantics are unchanged); the registry only supplies defaults for first creation.

Proven by: the Donations vertical (session 389, arc D3) — `donation_receipt` + `donation_acknowledgment` contributed at `register()`, consumed by the plugin's two mailables, the Giving Summary page, and the base seeder; with the plugin's manifest entry removed neither handle resolves defaults and the seeder seeds no donation rows. Second contributor (session 397, arc D7): the Forms plugin's two handles — `form_submission` (consumer: the plugin's observer → mailable) and `portal_form_collision` (consumer: the plugin's submission controller) — **the handle follows its consumer** (the 394 `portal_password_reset` principle, applied): both consumers travel with the plugin, so both handles moved out of core to the plugin's `register()` contribution, defaults byte-identical to the seeder rows they replace. This made the registry the single source of `portal_form_collision`'s defaults (the handle never had a core-array entry — the array/seeder disagreement recorded in the housekeeping inbox dissolved for this handle). **The three events handles remain in core's array** — migrating them is a `crm-plugin--events` release (backlogged); `admin_invitation` is now the only permanently core-owned handle (its consumer is the core admin-invitation flow). **`portal_password_reset` stays core for now, no longer "permanently"** (amended session 394): its consumer, the `PortalPasswordReset` mailable, stays core as model-adjacent (`PortalAccount`'s password-reset hook sends it — plan § 6.7), so the handle follows the mailable; if the model ever moves (D12 territory), the handle migrates to the portal plugin's registry contribution with it.

### 8. Importer registration — **PROVEN** (session 381)

Importers ship with their domain plugin. A plugin declares an `App\Plugins\ImporterContribution` into the core `App\Plugins\ImporterRegistry` singleton (bound by `PluginServiceProvider`, populated at plugin `register()` — the surfaces-3/13 pattern). The contribution pairs a slug with:

- **`pageClass` / `progressPageClass`** — the Filament wizard + progress pages (discovered via the plugin's surface-3 `pagesPath`; the registry only tells core's import surfaces which classes pair with which slug).
- **`label` / `icon` / `modelType`** — the importer-hub card, including the blocked-while-a-session-is-reviewing state.
- **`templateHeaders`** (closure) — the downloadable CSV template's header row, resolved by `CsvTemplateService::headersFor($slug)`.
- **`fakeSourceFieldMap`** (closure) — the saved field map for the seeded demo import source.

The per-importer composition (header prefixes, contact-match columns, transaction columns) is importer domain knowledge and lives in the plugin's closures, not in core consumers. Core consumers that resolve through the registry: the importer hub page + cards, the CSV-template streamer, the fixture runner's slug→progress-page pairing, and the demo-source/fake-CSV dev commands (which skip absent importers). Field-registry base classes (`FieldRegistry`, `AggregatingRegistry`, `DerivesFromFillable`) and the core-owned registries a plugin aggregates against (contact match, transactions) stay core. **Core-owned importers stay hard-wired in their consumers** — they can join the registry when their domains extract.

Proven by: the events importer (session 381) — three field registries + the preset column mapper + both wizard pages shipped in `plugins/Events/`, every core import surface resolving through the registry (`EventsPluginSession381Test`); with the plugin line removed the hub shows no events card, `headersFor('events')` throws, the demo source is skipped, and the import pages are gone (`EventsPluginRemovalSession381Test`).

### 10. Events / hooks — **PROVEN** (session 381 events slice; session 389 donations slice — the first cross-repo inversion; session 392 memberships slice — the second)

Laravel events for cross-plugin reaction. Plugins listen to core and foundation-plugin events; they never call into another vertical.

**Core owns three typed payment events** (all in `App\Payments\Events\`):

- **`CheckoutSettled`** (session 381) — a completed checkout session (the Stripe Checkout Session object + its metadata). The Payments webhook keeps the metadata routing switch — the metadata key is written by the vertical at session creation; routing is payments infrastructure — and each extracted vertical's branch body is: dispatch `CheckoutSettled`, return 200. **Listeners self-filter by their own metadata key** (`event_registration_checkout` for Events, `donation_id` for Donations, `membership_id` for Memberships): every bound listener receives every dispatch, so a listener must no-op cheaply — guard on the key first, before any read or log — on sessions routed to another vertical. *(The Events listener predated the second dispatcher and filtered only by `stripe_session_id` lookup — it gained its metadata guard in `crm-plugin--events` v0.1.1, released alongside session 389 so donation checkouts don't log spurious no-pending warnings.)*
- **`InvoiceSettled`** (session 389) — a paid subscription invoice (the Stripe Invoice object). Dispatched for **every** `invoice.payment_succeeded` carrying a subscription id; listeners resolve their own rows by subscription id (disjoint across verticals) and no-op on the rest.
- **`InvoicePaymentFailed`** (session 389) — a failed subscription invoice, same dispatch-always/self-filter shape.

**The events slice (session 381 — arc P5):** the Events plugin's listener (`PromotePaidRegistrations`) owns the former `event_registration_checkout` handler behavior — pending-promotion by `stripe_session_id`, contact resolution, one `Transaction::recordStripe` per order (a core write, allowed), one queued confirmation — idempotency identical. With Events absent the dispatch has no listener: 200, rows stay pending, data kept.

**The donations slice (session 389 — arc D3, the first cross-repo inversion):** the branches to invert lived in the extracted `crm-plugin--payments`, so the inversion is a **plugin release** — the post-extraction pattern: contract wording first, then the webhook change in the plugin repo, tagged (`v0.2.0`, minor — behavior change), then core's lock bump via `composer update nonprofitcrm/payments` in the same commit as the constraint widening (`^0.2` in `composer.json` **and** `distribution.json` — the guard enforces agreement) and the listeners that consume the new dispatches. Three Donations listeners own the former branch bodies verbatim: `PromotePaidDonations` (CheckoutSettled — promote by `donation_id`, one Transaction, queued acknowledgment behind the `acknowledged_at` per-gift idempotency marker), `RecordRecurringDonationPayment` (InvoiceSettled — the renewal Transaction + `donation_received` activity on true renewals), `MarkRecurringDonationPastDue` (InvoicePaymentFailed — past_due + the failed Transaction). Payments retains **zero** `Donation` model reads.

**The memberships slice (session 392 — arc D4, the second cross-repo inversion):** the two remaining membership branches inverted via a `crm-plugin--payments` **v0.3.0** release (the 389 release pattern exactly — contract wording first, webhook change in the plugin repo, tagged, core's lock bump + `^0.3` constraint widening in composer.json **and** distribution.json same-commit with the consuming listeners). The checkout `membership_id` branch becomes a dispatch (the third `CheckoutSettled` dispatcher); the `invoice.payment_succeeded` membership-renewal branch is a pure branch-delete — `InvoiceSettled` already dispatched for every subscription invoice since v0.2.0, so the Payments diff there removes the inline handler and nothing else. Two Memberships listeners own the former branch bodies verbatim: `PromotePaidMemberships` (CheckoutSettled — promote pending by `membership_id`, set the start/expiry window from the tier's billing interval, one Transaction; idempotent via the pending-status guard) and `RecordMembershipRenewal` (InvoiceSettled — extend the period, one Transaction per invoice id). **Membership invoice failures were never handled and remain unhandled** — no `InvoicePaymentFailed` listener exists by design (behavior preservation cuts both ways). Payments retains **zero** `Membership` model reads.

**The products slice (session 398 — arc D8, the third cross-repo inversion):** the webhook's last vertical-owned checkout branch inverted via a `crm-plugin--payments` **v0.4.0** release (the 389/392 release pattern exactly — contract wording first, webhook change in the plugin repo, tagged, core's lock bump + `^0.4` constraint widening in composer.json **and** distribution.json same-commit with the consuming listener). The checkout `product_price_id` branch becomes the fourth `CheckoutSettled` dispatcher; **branch ordering is load-bearing**: the metadata-keyed dispatch branches sit ahead of the generic fallback, so a product-tagged session dispatches and returns — it must never fall through to the generic Transaction write. One Products listener owns the former branch body verbatim: `RecordProductPurchase` (CheckoutSettled — record the Purchase by `product_price_id`, resolve-or-create the buying Contact from the Stripe customer details — a core `Contact` write, allowed — one Transaction; idempotent via the `stripe_session_id` guard carried over). The listener self-filter key list gains `product_price_id`. Payments retains **zero** `Purchase`/`ProductPrice` model reads.

**Per-vertical rollout:** the generic-fallback, refund, and failed-intent branches stay inline in Payments — they touch no vertical's models; each inverts to this surface if a future vertical claims it (via the release pattern above). That is the moment a webhook write would otherwise become a forbidden foundation→vertical reach.

Proven by: the events-slice tests (session 381), the donations-slice dispatch/listener/replay/no-listener tests plus the pre-existing donation webhook behavioral net passing through the dispatch path with assertions unchanged (session 389), and the memberships-slice listener/replay/self-filter/no-listener tests with the membership behavioral net unchanged (session 392).

### 11. Front-end assets — **PROVEN** (session 377)

A widget's `assets()` declares repo-relative `scss` / `js` file paths plus `libs` identifiers. `widgets:sync` writes them to `widget_types.assets`; `AssetBuildService::collectSources()` resolves each path via `base_path()` off disk — plugin paths (`plugins/{Name}/…`) resolve exactly like core paths. `build:public` compiles the bundle out-of-band on the build server and regenerates `public/build/widgets/manifest.json`.

**Vendor paths (Stage C-lite, session 385):** an extracted plugin declares its asset paths relative to the **consuming** repo's root — `vendor/{vendor}/{package}/…` (LogoGarden: `vendor/nonprofitcrm/logo-garden/styles.scss`; at scale, Events — session 388: five paths across three widget definitions under `vendor/nonprofitcrm/events/Widgets/…`, while EventsListing's declaration of the **core** BlogPager stylesheet stays a core repo-relative path — cross-plugin asset inputs don't move with the declaring plugin). The paths are opaque repo-relative strings to core; `AssetBuildService` and `widgets:sync` are untouched by extraction. (A `baseDir()`-derived declaration is a noted cleaner future shape — backlog, not built.)

**Cross-input resolution when the declared file itself leaves core (session 396 — arc D6, ADR 0007):** the recorded cross-input case resolved when the Blog carve moved the BlogPager widget folder out of core — the declared stylesheet was entirely the shared listing pager bar (consumed by EventsListing and BlogListing templates; BlogPager itself never declared it), and letting a sibling declare the *blog plugin's* vendor path would silently drop the rules from every blog-absent bundle (`collectSources()` skips missing paths). Per ADR 0007 (shared front-end dependencies are core-owned) the rules lifted to core-owned `resources/scss/widgets/_shared-pager.scss`; BlogListing and `crm-plugin--events` v0.1.3 (the rider — the 389/394 mechanics: contract wording → sibling edit → tag → core lock bump same-commit, `^0.1` unchanged) both declare the core path. A shared asset's home is core, never a sibling plugin; the declaring widgets carry only their own remainders.

**Caveat (by design, verify per extraction):** `collectSources()` silently skips paths that don't exist on disk — a stale path drops the asset from the bundle without erroring. After any asset-path change, run `widgets:sync` then `build:public` and confirm the manifest **and the built bundle content** actually carry the plugin's SCSS/JS (a green suite alone does not prove the bundle — the extraction runbook's gate 4). The pilot's sync test asserts every declared asset path exists on disk, vendor paths included since session 385.

Proven by: the pilot's SCSS + JS + `swiper` lib building from `plugins/LogoGarden/` into the served bundle (session 377, manifest + bundle-content verified).

### 13. Capability detection / soft dependencies — **PROVEN** (session 380)

A consumer can ask "is capability X present and enabled?" and must degrade gracefully when it isn't. Mechanics (session 380, arc P4):

- **`App\Plugins\CapabilityRegistry`** — core-owned singleton, bound by `PluginServiceProvider` alongside `PluginAdminRegistry` before any plugin registers. A foundation plugin declares `provide(string $name, Closure $enabled)` from its provider's `register()`; consumers ask `present($name)` (a registered plugin provides it) and `enabled($name)` (present AND the lazy resolver returns true — evaluated on every call, never cached).
- **Capability-scoped contracts are core-owned.** Alongside the boolean question, core owns the interfaces a capability's consumers program against — `App\Payments\Contracts\CheckoutProvider` (checkout-session creation + per-flow default image; callers rely only on the returned object's `->id`/`->url`) and `App\Payments\Contracts\PaymentModeProvider` (live-credential detection, consumed via the static `App\Payments\PaymentMode::isLive()`, false when nothing binds — an install without payments is never live). The plugin binds its implementations at `register()`; **nothing in `app/` may reference the `Plugins\Payments\` namespace, the Stripe SDK, or `services.stripe.*` config** — enforced with zero allowlist by the standing guard `tests/Feature/Infrastructure/PaymentModuleBoundaryTest.php`.
- **`payments`** is the first capability: resolver `filled(config('services.stripe.secret'))`, the same truthiness the five pre-carve controller guards tested. Remove the plugin's `config/plugins.php` line and present/enabled are false, every checkout endpoint returns its existing not-configured response, the webhook route is gone, and the free/$0 paths run untouched (`PaymentsPluginRemovalSession380Test`).
- **`member-portal`** is the second shipping capability (session 394 — arc D5): declared by the MemberPortal plugin at `register()` with resolver `fn () => true` — **presence is enablement** (unlike payments there is no credential dimension; a registered provider is a usable portal). Consumers: core's five `auth('portal')` reads (the surface-1 guard note — the guard exists only when the capability is present), and the `crm-plugin--events` portal registration route (v0.1.2 — registered only when present, the surface-4 alias note). The capability is the portal-presence signal for all composition-safety work: session 395's package phase gated the portal-*table* reads on it too (the contact-admin Portal Access section + the four EditContact portal actions, the `DemoPortalMemberSeeder` self-skip) and the seeded portal page topology (the surface-5 topology note).

Dependency rules (owner guideline, 376):

- **Verticals never depend on each other** — no vertical references another vertical's namespace, models, or code (the zero-allowlist boundary guards prove it in both directions).
- **Hard dependencies point only at core.**
- **Optional dependencies point at capability providers** (composer `suggests`, never `require`), consumed through capability detection — e.g. Events without Payments = free events only. Amended session 394: the provider side of an optional dependency is any plugin publishing a capability through the core-owned registry, not only a foundation plugin — the `member-portal` capability is published by a domain vertical, and Events' portal registration route consumes it (Events without Portal = public registration only, the route vanishes). The mediation is what keeps the rule intact: the consumer touches the core registry and core route names, never the providing plugin itself.

Proven by: five shipping vertical call sites (donation, product, membership, and both event-registration checkout controllers) plus `DashboardIntegrationStatusWidget` consuming `enabled('payments')`; the capability-semantics tests (`CapabilityRegistrySession380Test`) and the enabled/removal twin pair. **First in-plugin vertical consumer (session 381):** both event-registration controllers now consume `enabled('payments')` + `CheckoutProvider` from inside `plugins/Events/` — the vertical→foundation soft dependency in the flesh, tested across the full presence matrix (both present: the suite; Events without Payments: free/comp work, paid degrades — `EventsWithoutPaymentsSession381Test`; Events absent: the surface vanishes, data kept).

## Normative rules (apply to every plugin, every stage)

1. **Plugins never patch plugins** (plan principle 5). Extension happens through the surfaces above; two plugins never modify each other.
2. **Relations on `contact_id`, only** — see surface 9.
3. **Vertical/foundation dependency rules** — see surface 13.
4. **Disabled = inert, never destructive.** A disabled plugin registers no routes, contributes no nav, schedules no jobs, and stops writes — **its data is kept**. Enabling later is cheap; disabling never deletes. (Implemented by the surface-1 per-install activation layer, session 384: disabling stops the provider from registering — nothing deletes, migrates down, or mutates plugin data or schema.)
5. **Add-a-test discipline.** Every plugin carries tests for what it contributes; behavior a plugin adds is proven by tests that ship with the plugin. Formalized session 383 (arc P7): a packaged plugin's tests live in `plugins/{PascalName}/tests/`, registered as their own `phpunit.xml` testsuite so `php artisan test`, paratest, group filters, and CI run them unchanged (first consumer: the `Events` suite). Membership rule: a test moves into the plugin when its *subject* is plugin-owned behavior (controllers, observers, mailables, widgets, importer, admin pages, the plugin's twins/mirrors); it stays core when the plugin's records are merely fixture data for a core surface. The strip-the-line `RemovedTestCase` fixtures stay core — they are core's proof about core's loader.
6. **Contract honesty.** Surfaces here are marked PROVEN only when a shipped extraction exercises them.
